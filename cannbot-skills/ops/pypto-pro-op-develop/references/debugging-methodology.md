# PyPTO-Pro Kernel 调试方法论

> **目标读者**：pypto-pro-op-develop 子代理，在 Stage 4 验证进入 debug 状态时使用。
> **本文只讲「怎么想、按什么顺序查」**，不列具体错误码与修复代码——具体修复以运行时报错信息、API 文档原文、官方指定算子为准。

---

## 总纲

分层排查，不要东改一处、西试一处地随机试错。

- **先找到第一个出错的环节**：一个失败常是一条因果链的末端——比如公式或维度理解错了，会连带 layout 错、最终值全错。若从最下游的表象（值错）开始改，会陷入反复打补丁。应顺着「第二步：分层 review 顺序」从高层往低层查，定位到**最先偏离的那一层**（通常是公式语义或 layout），从那里修起。
- **先修模型，再修 kernel**：若根因在 DESIGN.md 或维度契约（模型层），先把模型改对，再动 kernel 代码；否则在错误设计上改出来的 kernel，迟早还要推倒重来。
- **不接受带告警的通过**：编译或运行告警通常说明你对某处机制的理解还不到位（比如同步或 buffer 生命周期没理清）。告警一直存在时，别再盲目试错，回到设计层重新想清楚，或向用户确认。

---

## 第一步：症状 → 检查方向 快查表

大多数失败都能归到下面某一类。先按症状找到要优先检查的方向，再进入下一节的分层排查。

| 症状（现象） | 优先检查方向 | pro 参考锚点 |
|--------------|--------------|--------------|
| **到处都错**（输出 shape 对但值大面积错） | 数学公式实现 / cast 顺序 / layout / 输入输出维度是否与 golden 一致 | `{op}_golden.py` 公式、DESIGN.md §0 维度契约 / §1 API 映射 |
| **只有大 shape 失败** | 片上容量（UB/L1/L0）是否超限 / tile 切分 / 归约轴是否可能超单 tile 却用了单 tile 假设 | DESIGN.md §2 Tile 规划 / §3 片上布局、`multi_core_partitioning_and_Tiling.md` §5.2 UB 预算 |
| **只有尾块失败**（整除通过、非整除失败） | 持久化 tile 的有效形状是否跨迭代残留未重置 / 边界切片 / 归约·matmul 尾块是否漏做填充 | `tail_block_handling.md` §3.1（有效形状裁剪搬运）、§4.2（归约/matmul 必须填充）、§8 常见坑 |
| **同步告警 / 流水结果异常** | 同侧计算排序与跨 section 数据交接是否混淆 / 多组流水事件是否隔离 / buffer 生命周期 | DESIGN.md §6 同步与核间流水、官方指定算子（FA/lightning）的跨核同步用法 |
| **整体精度对，个别位置 NaN/Inf** | 超越函数（exp/log/sqrt 等）在目标 dtype 下是否溢出 | DESIGN.md §1 超越函数数值安全边界 |
| **多核结果错 / 累加异常** | 分核是否重叠或遗漏 / 累加语义（覆盖写 vs 原子累加）/ 累加前输出是否需预清零 | `multi_core_partitioning_and_Tiling.md` §2 跨步循环、`原子操作/store_atomic.md` |

> 表中「优先检查方向」只指出应先看哪里。**具体错误码 → 根因 → 修复**以运行时抛出的报错信息与 API 文档原文为准，不套用固定结论。

---

## 第二步：分层 review 顺序

当快查表未命中、或按方向查后仍未定位时，按下面从高到低的层级逐层排查。**高层错会向下传导，务必按序**，不要跳过上层直接改底层代码。

> 每层只说明**该查什么概念**；具体 API 写法与参数以下方括号里指向的活文档（DESIGN 对应轮次 / API 文档原文 / 官方指定算子）为准，本文不复述，以免随框架演进过期。

1. **公式语义与 cast 顺序**
   算子实际算的东西是否与 golden 一致：公式实现、cast 时点、转置/变形语义、输入输出维度有无偏差。若算子要算什么本身还不清楚，停下澄清，别改代码。（DESIGN.md §0 维度契约 / §1 API 映射）

2. **layout**
   各 tile 的 layout 是否满足所用 API 的要求。具体 layout 取值以 API 文档与 DESIGN 为准。（DESIGN.md §2/§3、相关 API 文档）

3. **tile 与片上容量**
   各片上内存空间的 tile 总占用是否分别超出各自容量；tile 切分是否合理。（DESIGN.md §3 逐空间用量、EXPLORE_REPORT §7 容量、`multi_core_partitioning_and_Tiling.md` §5.2）

4. **尾块处理**
   tile 数是否向上取整；每轮迭代是否重置持久化 tile 的有效形状（有效形状是有状态的，跨迭代会残留）；归约/matmul 尾块是否做了填充。核心心智：物理形状固定、有效形状随位置变。（`tail_block_handling.md` §3/§4/§8）

5. **同步与所有权**
   区分两类同步——同侧计算的先后排序，与跨 section 的数据交接，二者机制不同、不可互相替代；确认生产方在数据产生后发信号、消费方在使用前等信号；多组流水的事件是否互相隔离。（DESIGN.md §6、官方指定算子（FA/lightning）的跨核同步用法）

6. **分核与流水生命周期**
   分核是否覆盖全部 tile、有无重叠或空转；多缓冲的地址与同步是否随缓冲份数正确规划；跨 tile 的状态（如 running max/sum）是否正确初始化与持久化。（`multi_core_partitioning_and_Tiling.md` §2/§5.3、DESIGN.md §5/§6）

7. **数值边界**
   值在何处改变 dtype：是否过早降精度、是否在不合适的 dtype 下归约、matmul 累加精度是否足够、超越函数是否可能溢出。（DESIGN.md §1 数值安全边界）

8. **实现路径**
   前面仍定位不到时，查具体 API 文档原文与官方指定算子的真实写法：这条 API 实际接受什么参数、运行时如何执行、kernel 的假设是否与之一致，以实际证据修正 DESIGN.md 的失误。

## 第三步：构建最小复现

当完整 kernel 干扰因素太多、难以定位时，把单一机制单独拎出来复现，通常比盯着整个融合 kernel 推敲更快。

- **隔离对象**：单个 Phase / 单条关键 API / 单块 tile / 一次 cube→vec 交接 / 一个尾块场景。
- **收缩顺序**：
  1. 保留触发失败的原始 shape；
  2. 删掉后续 Phase，只留到第一个出错的 Phase；
  3. 在该 Phase 内只保留一个子公式（如一次归约、一次 matmul、一个 GM 搬运）；
  4. 必要时再缩到一条 API + 一个 tile 视图。
- 隔离出错误后，先在最小复现上修正，再回到完整 kernel 重跑。

> 最小复现与「增量验证」思路一致：先跑通一个最小的可验证片段，再逐步加回后续 Phase 和尾块 case，避免写完整个融合 kernel 才第一次运行。

---

## 第四步：升级与切换

当反复修复仍无法通过时，必须识别"是否在同一错误模式上打转"，并按规则切换方向。

### 错误模式识别

"同一错误模式"指连续 3 次修复尝试后，失败现象属于以下同一类别：
- **同一类编译错误**：如连续 3 次 dtype/layout 不匹配，只是换了不同 tile
- **同一类运行时错误**：如连续 3 次 AICore timeout，只是改了不同 sync 参数
- **同一类精度错误**：如连续 3 次同一区域/同一列值错，只是调了不同计算顺序

### 切换规则

识别到"同一错误模式连续 3 次"后，**立即停止当前修复方向**，按以下顺序切换：

1. **回到更高层级排查**：按第二步分层顺序，回到比当前排查层更高的一层重新审视。例如当前在"同步与所有权"层反复失败，回到"layout"甚至"公式语义"层重新检查。
2. **构建最小复现**：若已在最高层（公式语义）排查，按第三步构建最小复现，隔离单一机制。
3. **尝试完全不同的实现路径**：若最小复现也失败，停止在当前路径上反复修补——在 MEMORY.md 中记录已尝试的方案清单（每种方案 + 失败原因）和已排除的方向（为什么不可行），然后尝试从完全不同的角度重新实现（如换用不同的 API 序列、不同的 tile 分块策略、不同的同步方案）。

---

## 边界说明

- 本文只承载**通用调试思路**，不含 pro 专属错误码表与逐条修复方案。
- 所有排查方向最终都应落到**可验证的证据**：运行时报错信息、API 文档原文、官方指定算子、DESIGN.md 对应轮次。
- 若排查指向 DESIGN.md 的设计失误，按 SKILL.md 步骤 7「Debug 状态下的决策权限」据实修正并记录到 MEMORY.md。
