## <a id="overview"></a>总纲

分层排查，不要东改一处、西试一处地随机试错。

- **先找到第一个出错的环节**：一个失败常是一条因果链的末端——比如公式或维度理解错了，会连带 layout 错、最终值全错。若从最下游的表象（值错）开始改，会陷入反复打补丁。应顺着「第二步：分层 review 顺序」从高层往低层查，定位到**最先偏离的那一层**（通常是公式语义或 layout），从那里修起。
- **先修模型，再修 kernel**：若根因在 DESIGN.md 或维度契约（模型层），先把模型改对，再动 kernel 代码；否则在错误设计上改出来的 kernel，迟早还要推倒重来。
- **失败计数是证据，不是结论**：先确认你看到的失败数量和内容是它看起来的意思（见第零步），
  再开始分层。一次设备故障、一份旧二进制，都会让简单问题伪装成"kernel 大面积错"。
- **不接受带告警的通过**：编译或运行告警通常说明你对某处机制的理解还不到位（比如同步或 buffer 生命周期没理清）。告警一直存在时，别再盲目试错，回到设计层重新想清楚，或向用户确认。

## <a id="verify-failure"></a>第零步：先确认"失败现象"本身是可信的

**在定位之前，先确认你看到的失败数量和失败内容，是它看起来的那个意思。**
下面三种情况都会让一次简单故障伪装成"kernel 大面积错"，从而把整轮排查引向错误的层级：

| 现象 | 真实原因 | 怎么确认 |
|---|---|---|
| **前面某个 case 失败后，其后所有 case 全失败**（报 `copy_between_host_and_device` 之类） | **一次设备故障会污染 NPU 上下文**，后续 case 是被连坐的，不是各自出错 | **只跑那个最先失败的 case**。一次实测中，一个 case 触发故障后其后 **16 个 case 全部失败**，看起来像 kernel 整体崩了，实际只有一个形状有问题 |
| **全部 case 失败，且报错来自 `npuSynchronizeDevice` / 拷贝入口的 `RuntimeError`，而不是精度指标** | **比对根本没跑**，多半是卡坏了 | 先读 `npu-smi`（只读、一次往返）。判别细则见 [`pypto-pro-environment-check`](../../pypto-pro-environment-check/SKILL.md)「设备故障伪装成精度失败」 |
| **改了代码，结果逐字节和上次相同**（"我的改动没生效"） | 可能收到**旧二进制**——构建目录按 kernel 名索引，body 变了名字没变就会命中缓存 | 让 kernel 名带上 body 内容哈希，或清掉构建目录再跑。**注意哈希要覆盖编译器真正看到的东西**：只哈希渲染出的 wrapper，会让这个保护对它本该拦的改动完全失效 |

**失败计数是证据，不是结论。** 先把"一个真故障"和"N 个独立故障"分开，再进入分层排查。

## <a id="symptom-map"></a>第一步：症状 → 检查方向 快查表

大多数失败都能归到下面某一类。先按症状找到要优先检查的方向，再进入下一节的分层排查。

| 症状（现象） | 优先检查方向 | pro 参考锚点 |
|--------------|--------------|--------------|
| **到处都错**（输出 shape 对但值大面积错） | 数学公式实现 / cast 顺序 / layout / 输入输出维度是否与 golden 一致 | `{op}_golden.py` 公式、DESIGN.md §0 维度契约 / §1 API 映射 |
| **只有大 shape 失败** | 片上容量（UB/L1/L0）是否超限 / tile 切分 / 归约轴是否可能超单 tile 却用了单 tile 假设 | DESIGN.md §2 Tile 规划 / §3 片上布局、`multi_core_partitioning_and_Tiling.md` §5.2 UB 预算 |
| **只有尾块失败**（整除通过、非整除失败） | 持久化 tile 的有效形状是否跨迭代残留未重置 / 边界切片 / 归约·matmul 尾块是否漏做填充 | `tail_block_handling.md` §3.1（有效形状裁剪搬运）、§4.2（归约/matmul 必须填充）、§8 常见坑 |
| **同步告警 / 流水结果异常** | 同侧计算排序与跨 section 数据交接是否混淆 / 多组流水事件是否隔离 / buffer 生命周期 | DESIGN.md §6 核间同步、官方指定算子（FA/lightning）的跨核同步用法 |
| **整体精度对，个别位置 NaN/Inf** | 超越函数（exp/log/sqrt 等）在目标 dtype 下是否溢出 | DESIGN.md §1 超越函数数值安全边界 |
| **多核结果错 / 累加异常** | 分核是否重叠或遗漏 / 累加语义（覆盖写 vs 原子累加）/ 累加前输出是否需预清零 | `multi_core_partitioning_and_Tiling.md` §2 跨步循环、`原子操作/store_atomic.md` |
| **失败恰好按 dtype（或某个配置）整齐划分**，同一份数学在别的 dtype 上完全正常 | 不是数学问题，先怀疑**生成代码里的标识符冲突**——参数名/变量名撞上目标语言的类型名或关键字，会让该 dtype 的每个 kernel 都编译失败，且报错指向看似无关的位置 | 直接看生成出来的源码，而不是模板 |
| **同一配置下，一个 shape 过、另一个不过**（tile 档位、layout、代码路径全相同） | 判别属性是**两者真正不同的那一项**，而它通常是**取值范围**，不是 shape | 对比两个 case 的 `value_range` 而不是 dims；下溢/溢出只在特定量级出现 |
| **精度整体对，但个别位置结果与参考差一个"语义"**（NaN/Inf、±0、边界值） | 某次化简/优化**删掉了一步运算**，而那步正是在处理特殊值 | 问"被删掉的那步在为特殊值做什么"，再问"公开用例能不能构造到那个输入" |
| **改完后本 case 好了，别的 case 变差** | 修改动到了共享路径（tile 预算、循环结构、mask） | 见「第五步：修正之后」——回归没碰过的 case |

> 表中「优先检查方向」只指出应先看哪里。**具体错误码 → 根因 → 修复**以运行时抛出的报错信息与 API 文档原文为准，不套用固定结论。

## <a id="layered-review"></a>第二步：分层 review 顺序

当快查表未命中、或按方向查后仍未定位时，按下面从高到低的层级逐层排查。**高层错会向下传导，务必按序**，不要跳过上层直接改底层代码。

> 每层只说明**该查什么概念**；具体 API 写法与参数以下方括号里指向的活文档（DESIGN 对应轮次 / API 文档原文 / 官方指定算子）为准，本文不复述，以免随框架演进过期。

1. **公式语义与 cast 顺序**
   算子实际算的东西是否与 golden 一致：公式实现、cast 时点、转置/变形语义、输入输出维度有无偏差。若算子要算什么本身还不清楚，停下澄清，别改代码。（DESIGN.md §0 维度契约 / §1 API 映射）

2. **layout**
   各 tile 的 layout 是否满足所用 API 的要求。具体 layout 取值以 API 文档与 DESIGN 为准。（DESIGN.md §2/§3、相关 API 文档）

3. **tile 与片上容量**
   各片上内存空间的 tile 总占用是否分别超出各自容量；tile 切分是否合理。（DESIGN.md §3 逐空间用量、EXPLORE_REPORT §7 容量、`multi_core_partitioning_and_Tiling.md` §5.2）

4. **尾块处理**
   tile 数是否向上取整；每轮迭代是否重置持久化 tile 的有效形状（有效形状是有状态的，跨迭代会残留）；归约/matmul 尾块是否做了填充。核心心智：物理形状固定、有效形状随位置变。（`tail_block_handling.md` §3/§4/§8）

5. **同步与所有权**
   区分两类同步——同侧计算的先后排序，与跨 section 的数据交接，二者机制不同、不可互相替代；确认生产方在数据产生后发信号、消费方在使用前等信号；多组流水的事件是否互相隔离。（DESIGN.md §6、官方指定算子（FA/lightning）的跨核同步用法）

6. **分核与流水生命周期**
   分核是否覆盖全部 tile、有无重叠或空转；多缓冲的地址与同步是否随缓冲份数正确规划；跨 tile 的状态（如 running max/sum）是否正确初始化与持久化。（`multi_core_partitioning_and_Tiling.md` §2/§5.3、DESIGN.md §5/§6）

7. **数值边界**
   值在何处改变 dtype：是否过早降精度、是否在不合适的 dtype 下归约、matmul 累加精度是否足够、超越函数是否可能溢出。（DESIGN.md §1 数值安全边界）

8. **实现路径**
   前面仍定位不到时，查具体 API 文档原文与官方指定算子的真实写法：这条 API 实际接受什么参数、运行时如何执行、kernel 的假设是否与之一致。若证据推翻 DESIGN.md，返回 `design_violation` 交编排器回退 Stage 3；本阶段不直接改写设计。

## <a id="minimal-reproduction"></a>第三步：构建最小复现

当完整 kernel 干扰因素太多、难以定位时，把单一机制单独拎出来复现，通常比盯着整个融合 kernel 推敲更快。

- **隔离对象**：单个 Module / 单条关键 API / 单块 tile / 一次 cube→vec 交接 / 一个尾块场景。
- **收缩顺序**：
  1. 保留触发失败的原始 shape；
  2. 删掉后续 Module，只留到第一个出错的 Module；
  3. 在该 Module 内只保留一个子公式（如一次归约、一次 matmul、一个 GM 搬运）；
  4. 必要时再缩到一条 API + 一个 tile 视图。
- 隔离出错误后，先在最小复现上修正，再回到完整 kernel 重跑。

> 最小复现与「增量验证」思路一致：先跑通一个最小的可验证片段，再逐步加回后续 Module 和尾块 case，避免写完整个融合 kernel 才第一次运行。

**最小复现是"往下减"。下面两种是"往上加"和"横着换"，在定位代价/瓶颈时往往更直接。**

### 消融法：一次加回一个阶段

从只做搬运的骨架开始，**每次只加回一个阶段**，每加一次都测一次。
它把代价/误差**归属到某一个阶段**，而不是靠猜。

实测形态（同一个形状，逐级累加）：

```
只 load+store        10.46 us
  + dtype 转换       13.81 us     (+3.35)
  + 归约             59.18 us     (+45.37)   <-- 70% 在这里
  完整 kernel        65.10 us
```

结论不是"归约慢"这种感觉，而是"**归约占 70%**，其余全部加起来不到三成"——
优化和排查的顺序由此确定。同样的做法可用于精度：逐级加回并每级比对 golden，
第一个偏离的阶段就是根因所在。

### 单原语替换：一次只换一个，且**保持真实依赖深度**

要知道某个原语值不值这个钱，就在**真实循环里**一次只替换它一个，其余不动。

**不要用"两条指令的微基准"去测它**——那种循环没有真实的依赖链和发射压力，
测出来的倍率会严重偏小，据此做的设计决策会整个错掉。
实测差异：真实依赖深度下，跨 lane 原语是相邻访问的 **20–35 倍**；
而一个两指令微基准会让人以为只差几倍。

### 差异属性二分：两个 case 一过一不过时

不要去比"哪里不一样"的全部清单，而是**只保留两者真正不同的那一项**去构造用例。
同 tile 档位、同 layout、同代码路径下一过一不过时，判别属性通常是
**取值范围**（下溢/溢出）而不是 shape——按范围设门，不要按档位设门。

## <a id="escalation"></a>第四步：升级与切换

当反复修复仍无法通过时，必须识别"是否在同一错误模式上打转"，并按规则切换方向。

### 错误模式识别

"同一错误模式"指连续 3 次修复尝试后，失败现象属于以下同一类别：
- **同一类编译错误**：如连续 3 次 dtype/layout 不匹配，只是换了不同 tile
- **同一类运行时错误**：如连续 3 次 AICore timeout，只是改了不同 sync 参数
- **同一类精度错误**：如连续 3 次同一区域/同一列值错，只是调了不同计算顺序

### 切换规则

识别到"同一错误模式连续 3 次"后，**立即停止当前修复方向**，按以下顺序切换：

1. **回到更高层级排查**：按第二步分层顺序，回到比当前排查层更高的一层重新审视。例如当前在"同步与所有权"层反复失败，回到"layout"甚至"公式语义"层重新检查。
2. **构建最小复现**：若已在最高层（公式语义）排查，按第三步构建最小复现，隔离单一机制。
3. **尝试完全不同的实现路径**：若最小复现也失败，停止在当前路径上反复修补——在 MEMORY.md 中记录已尝试的方案清单（每种方案 + 失败原因）和已排除的方向（为什么不可行），然后尝试从完全不同的角度重新实现（如换用不同的 API 序列、不同的 tile 分块策略、不同的同步方案）。

## <a id="post-fix"></a>第五步：修正之后

**修好一个 case 不等于修对了。** 三条按顺序做：

1. **跑相反分支的 case。** 一个 case 变好不能证明结构对——必须找一个走**另一条分支**的形状
   来跑。实测：一次循环结构调整让非整除形状改善 1.31%，同一次改动却让**整除形状劣化 1.65×**
   （112.7 → 186.5 µs），因为整除时每一行都要付一次零次迭代的循环建立开销。
   只跑改善的那个 case 就会把劣化当成收益交付。
   **判断"相反分支"的方法**：看你改的代码里有哪个条件（尾块是否为空、是否走多 pass、
   mask 是否满），构造一个让它取另一个值的形状。
2. **回归没碰过的 case。** 修改若动到共享路径（tile 预算、循环结构、mask、pitch），
   影响面不止目标 case。**至少把全量 case 跑一遍**，别只跑失败过的那几个。
3. **记录"原方案 → 修正方案 + 依据"**（SKILL.md 步骤 7 ③）。特别是**否定结论要连条件一起记**：
   "无效果"会过期，"在 X 比它大 1.5 倍的情况下测得无效果"不会。上游变了要回来重开这个结论。

**改之前先备份。** 每一次对"已经能跑通"的代码做重构，都是一个候选回退点，复制一份只要一条命令。

## <a id="diagnostic-discipline"></a>诊断纪律

三条都在本轮实际造成过错误结论，且都不是粗心，而是看起来完全合理的推理。

- **不要从被截断的搜索里断言"不存在"。** 一次 `grep | head` 的输出被当成完整结果，
  据此断言某个 API 不存在；它其实存在于同一文件更靠后的位置。
  **这是误报 `capability_gap` 的最常见来源**——在说"框架不支持"之前，
  确认你的搜索没有被 `head`/`tail`/分页截断，并把 API 文档与官方样例都真正查过。
- **复制出来的 helper 不会收到后续修复。** 因为 import 不方便就把公共函数复制到自己的探针里，
  等公共版本修好之后，**所有副本仍带着老 bug**，而且它们正是做设计决策的地方。
  想办法 import 共享实现（必要时 stub 掉挡路的模块），让探针跟随主线而不是快照主线。
- **打印不变量还不够，得有人或断言去核对它。** 一个"看着不太对"的计数被搁置了四轮才被理解。
  更好的做法是让程序打印**它走了哪条分支**（而不只是数值），使结论事后可核验，
  而不是只能靠"当时应该没问题"。

---

## <a id="boundaries"></a>边界说明

- 本文只承载**通用调试思路**，不含 pro 专属错误码表与逐条修复方案。
- 所有排查方向最终都应落到**可验证的证据**：运行时报错信息、API 文档原文、官方指定算子、DESIGN.md 对应轮次。
- 若排查指向 DESIGN.md 的设计失误，按 SKILL.md 步骤 7「Debug 状态下的决策权限」据实修正并记录到 MEMORY.md。
