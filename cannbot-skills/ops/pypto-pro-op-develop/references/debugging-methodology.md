本文用于 Stage 4 的编译、运行或精度失败。只规定排查顺序；具体 API、错误含义和修复写法以目标版本 API 文档、官方指定算子、`DESIGN.md` 与原始运行证据为准。

## <a id="verify-failure"></a>先确认失败可信

在修改代码前，先证明观察到的是独立、当前且可复现的失败：

1. 找出最先失败的 case，单独重跑它。设备故障可能污染 NPU 上下文，使后续 case 连带失败；不要把一次故障计成多个 kernel 缺陷。
2. 区分精度失败与运行环境失败。若比对逻辑尚未执行，错误来自设备同步、拷贝、导入、CANN 或设备不可见，加载 `pypto-pro-environment-check` 按其流程评定，不在本阶段改环境。
3. 确认运行的是当前源码。若修改后结果与旧结果完全一致，检查构建缓存和实际编译输入；重新运行时保留命令、源码版本和原始输出。
4. 在干净上下文中重复最小失败一次。只把可稳定复现的首个失败带入后续分层排查。

失败次数只描述现象，不自动证明根因。

## <a id="symptom-map"></a>按症状选择方向

| 症状 | 优先检查 |
|---|---|
| shape 正确但值大面积错误 | 公式、cast 时点、输入输出语义、layout |
| 仅大 shape 失败 | 各片上空间容量、tile 切分、跨 tile 状态 |
| 仅尾块失败 | valid-shape 重置、边界索引、归约或 matmul 填充、store 范围 |
| 同步告警或流水结果异常 | 数据所有权、生产/消费顺序、event 隔离、buffer 生命周期 |
| NaN、Inf、±0 或边界值异常 | dtype、运算顺序、超越函数范围、被省略的特殊值语义 |
| 多核遗漏、重叠或累加异常 | work-item 覆盖、写入所有权、覆盖/累加语义、初始化 |
| 失败按 dtype 或配置整齐分组 | 目标版本支持、生成源码标识符、dtype/layout 合同 |
| 同路径下一组值过、一组值不过 | 比较真实差异属性，尤其 `value_range`，不要只比较 shape |
| 修好目标 case 却破坏其他 case | 共享循环、tile、mask、pitch 或分支受到影响 |

快查表只选择起点，不代替原始错误和文档证据。

## <a id="layered-review"></a>按层定位根因

从高层到低层寻找第一个偏离合同的位置。高层错误会向下传播，先修最早偏离的一层。

1. **数学和维度**：kernel 是否实现 golden 的公式、cast 顺序、变形语义和 I/O 维度；核对 DESIGN.md §0/§1。
2. **layout 与 API**：每个调用的原型、参数顺序、dtype、layout、MemorySpace 是否符合目标版本文档和 working example；核对 DESIGN.md §1–§3。
3. **tile 与容量**：每个内存空间分别计量，核对 tile 属性、地址重叠、切分和动态 valid-shape；核对 DESIGN.md §2/§3。
4. **尾块**：检查向上取整、每轮 valid-shape 重置、填充值和最终 store 窗口；核对 DESIGN.md §7。
5. **同步与所有权**：区分核内 pipe 互斥与跨核数据交接；核对信号发送/等待位置、event_id、buffer 生命周期；核对 DESIGN.md §4–§6。
6. **分核与跨 tile 状态**：确认 work-item 全覆盖且不重叠，running state 初始化、保存和更新正确；核对 DESIGN.md §5/§6。
7. **数值边界**：确认提升与降精度位置、归约/累加 dtype、特殊值和超越函数范围；核对 DESIGN.md §1 和实际测试范围。
8. **实现路径**：前述均无偏差时，读取 PRO_MATERIAL_INDEX.md 指向的 API 原文和官方样例，验证当前写法是否真实受支持。

若第一个偏离点来自 DESIGN.md，而不是 Stage 4 的抄录或翻译错误，停止在 kernel 上打补丁并按 `design_violation` 分流。

## <a id="isolate"></a>缩小与验证假设

完整 kernel 难以定位时，一次只隔离一个机制。

### 最小复现

保留触发失败的原始关键条件，然后依次收缩：

1. 截断到第一个出错的 Module；
2. 只保留该 Module 的一个子公式或一次数据交接；
3. 缩到一条 API、一个 tile 和一个边界场景；
4. 在最小复现上修复后，再逐步恢复 Module、分支和尾块。

保留原始 shape、dtype、value range 或同步关系中真正触发问题的条件，避免把失败一起删掉。

### 消融

从可验证的 load/store 骨架开始，每次只加回一个阶段并立即与 golden 比对。第一个出现误差或错误的阶段就是下一步调查对象。不要同时改多个阶段，否则无法把结果归因到单一修改。

### 单因素替换

比较 API、tile 或同步方案时，只替换一个因素，其余循环、数据依赖与测试保持不变。使用真实依赖深度和目标 case，避免用不具代表性的微型路径推导完整 kernel 结论。

### 差异属性二分

两个 case 一过一不过时，固定共有属性，只改变一个候选差异，如 shape、dtype、value range、尾块、分支或核数。用结果排除假设，直到找到最小判别条件。

## <a id="route"></a>按归属处理

| 根因归属 | 处理 |
|---|---|
| 当前 Stage 的调用抄录、局部索引、实现或测试错误 | 修复实现，保留复现和验证证据 |
| DESIGN.md 的维度、API 序列、tile、循环、同步、尾块或 `vector_selection` | 返回 `design_violation`，附合同位置、原始错误和最小复现；不编辑 DESIGN.md |
| 目标版本框架能力不足 | 先完整查阅 API 文档、官方样例和教程，并测试 DESIGN 允许的候选；证据充分后返回 `capability_gap`，列出版本、命令、原始输出与已排除方案 |
| 环境、设备或疑似 hang | 使用 `pypto-pro-environment-check` 评定，交给编排器分流；不要用临时短超时探针代替其流程 |

新证据推翻当前方向时立即回到更高层或换用最小复现，不按固定尝试次数机械重复同一种修补。不得用 host 核心计算掩盖设计或能力问题。

## <a id="post-fix"></a>修复后回归

修好单个 case 后按顺序验证：

1. 重跑最小复现，确认目标根因已消失，而不只是错误位置变化。
2. 运行一个经过相反分支的 case，例如整除与尾块、单 tile 与跨 tile、单核与多核。
3. 运行 DESIGN.md §8 的全部 case，检查精度、运行错误和告警。
4. 若修改共享路径，重点复核所有受影响的 Module、dtype、shape 和 value range。
5. 记录运行命令、原始结果摘要、修改前后的不变量以及仍未解释的风险。

全量回归通过且没有未解释告警，才退出 debug 状态。自验证通过不等于 verifier PASS。
