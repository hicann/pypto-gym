# PyPTO-Pro 算子交付

## 目标与范围

将任意来源的已跑通 kernel 接入官方 CANN 工程，交付可安装、可调用且有真实验收证据的自定义算子。不绑定业务仓，不修改 kernel 的数学算法、数据排布、多核协作、同步或精度策略。

默认生成并验证 **ACLNN + GEIR**；用户明确选择单路时，只验收该路：

- 基础交付件：`op_api`（ACLNN 接口）、host tiling（CPU 侧切分与启动参数）、OpDef（算子信息库）和 `op_kernel`（PyPTO-Pro kernel）。
- 包含 GEIR 时，再增加 `op_graph`（算子原型）和 inferShape/inferDtype（输出形状、类型推导）；仅 ACLNN 时不纳入这些独立文件。

本 Skill 负责 PyPTO-Pro 接入与交付闭环。通用工程和调用骨架复用 `CANN/cannbot-skills` 的注册调用模板，精度规则复用其精度 Skill；不复制示例算法或重建通用脚本框架。

用户仅要求评审或解释时，只读核对相关阶段及现有证据，不自动生成、构建、安装或修复。

## 输入与责任边界

开始前收齐：

- kernel 文件、参与编译的本地辅助文件（不含基线库）、`@pl.jit` 入口、调用它的 Python wrapper；
- 环境初始化、原始测试命令及其正确结果或比对方法；目标芯片（SoC）和 CANN/PyPTO-Pro 版本；
- 本地 PyPTO-Pro 文档或源码根、`CANN/cannbot-skills` 根、支持当前 PyPTO-Pro 离线编译和入包的 CANN 构建根；
- 本轮输出目录（未指定时建立独立目录），以及已有公开接口要求（如有）。

外部根未提供时，一次性询问本地路径；不扫描、猜测、下载或用历史缓存替代。路径无效时报告路径、原始错误及需要补齐的内容。记录所用根的 Git HEAD 和相关未提交修改；无 Git 时记录所读文件的 SHA-256。

调用方须保证原始 kernel 及其环境、依赖、测试重跑方式可用，且不存在原始 kernel 的真实离线编译、运行或精度问题；Agent 仍须实际验证，不能以用户保证替代证据。遇到这些前提问题，报告失败命令、原始错误和调用方需修复的事项，等待补齐；不自行安装、升级或改换依赖，也不改测试或正确结果绕过失败。

本轮生成工程的接口、切分参数、注册、构建和调用接入错误，由 Agent 在工程副本内修复并重验。先排除这些错误再归因于环境；内置示例也失败不是充分证据。不得修改 CANN 安装目录、执行设备级恢复或终止非本轮进程。

## 工作流

按依赖顺序推进，前一阶段通过再进入下一阶段。关键命令保留完整 stdout/stderr、真实退出码及输入/产物 SHA-256；重试使用新的记录目录，保留失败证据，不让管道或后续成功命令掩盖失败。

### 1. 运行原始测试

在本轮独立工作目录按给定顺序初始化环境并运行原始测试，JIT/cache/tmp 均放入本轮目录，来源保持只读。确认实际使用 `pypto_pro.language` 和 `@pl.jit`。退出码为 0 且输出符合原测试正确结果后，才开始生成交付件。

### 2. 确定公开接口和构建入口

在提供的 PyPTO-Pro 根中查阅当前离线 codegen、TilingData、TilingKey 和 JIT 参数文档。路径未知时，可加载 gym 内 [pypto-docs-search](../pypto-docs-search/SKILL.md) 复用检索方法，但不执行下载/缓存装配；独立安装缺少该 Skill 时，直接在已提供根内检索。

建立工程前，完整加载 `CANN/cannbot-skills` 根下的 `ops/ascendc-registry-invoke-template/SKILL.md`，按其路由读取所选通路的工程、构建安装、host 单元测试和调用模板。只复用通用结构与方法，不照搬示例的接口、数据类型、形状、切分公式或分支值。Python JIT 不使用 `ascendc-direct-invoke-to-registry-invoke`。

将公开契约（调用者可见的接口约定）写入交付目录：算子注册名（OpType）与 ACLNN 名称、通路、输入/输出/属性的数量和类型、布局、形状及取值范围、相互关系和地址共用规则。列出公开参数到 kernel 参数的顺序/类型，以及 wrapper 计算启动核数、临时内存和切分参数的公式。包含 GEIR 时检查与内置算子重名的风险。

契约缺项时，列出从源码、wrapper、成功测试和官方文档推导的方案及验证方法，询问是否代补并说明默认代补；用户明确拒绝则等待其补齐。无既有接口要求时采用新的无冲突私有名称；无法由证据确定的业务语义或算法选择交由用户决定，不冒充同名公共算子。

从模板入口沿当前通用构建脚本和 CMake include/add_subdirectory 链，核实算子发现方式、`op_class`（落盘分类，可为无）、目标 SoC、configure/build/package/install 参数及最终 host/kernel 目标。完整读取 `enable_pypto_kernel` 或等价接口的真实定义与签名；不以函数名存在代替能力验证，也不读取构建根内已有业务算子作参考。仍缺入口时请用户指定；确无官方离线接口时报告 `official-offline-integration-missing`，不自造替代编译框架。

确认后，将构建根复制到本轮输出目录，排除根层 `.git`、旧 `build`/`build_out`/`output`，保留权限与符号链接，不跟随链接写入来源。所有生成、构建和安装均使用本轮副本及新目录；保存来源清单，结束时核对未变。

### 3. 对齐 CPU 参数与 kernel，生成完整工程

先完整读取 [接入与验收细节](references/integration.md)，执行其中“参数与注册”要求。建立公开参数、wrapper 公式、kernel 参数、运行数据（TilingData）、已编译分支（TilingKey）、核数和临时内存的候选映射。

用官方 `pypto_codegen.py` 或当前等价接口，对拟交付签名、TilingData 和 TilingKey 做一次真实生成试验。以新生成头文件消除类型、参数槽、文件名和分支编码的不确定项；不得 mock、monkeypatch 编译链或伪造生成头。官方驱动自带的非编译依赖导入占位不等于伪造编译。

映射确定后，按已加载模板和所选通路生成完整目标树，并接入真实构建目标。公开约束须由实际经过的 OpDef、API、图推导或 host 层实施，不能只写在契约中；以非法输入验证检查可达。

### 4. 验证改造等价，配置真实构建

直接加载原 kernel 和最终 `op_kernel`，保留原测试的输入构造、测试装饰器、编译/运行选项、比较方法和容差，验证两份实际 JIT 输出一致，或分别通过原测试正确结果比对。不得另造参考结果降低要求；核对 wrapper 公式全部对应到 host。

设计任何新增精度数据、正确结果、检查器或容差前，完整加载 `CANN/cannbot-skills` 根下的 `ops/ops-precision-standard/SKILL.md`，读取其选中的类别规范、`references/benchmark_construction.md`、`references/test_case_generation.md` 和所用检查器实现。若更早需要这些工作，提前加载。用例、标杆、指标和阈值均由该 Skill 决定。

按参考文件的“构建与入包”要求，在全新 build 目录完成 clean configure，确认共享头是本次生成的、最终 kernel 已进入真实构建图；随后沿同一配置继续构建，不重配成另一组值。

### 5. 联调 host，构建并安装算子包

依次完成：编译承载本算子 tiling 的 host 共享库 → 从正式注册表真实执行 host 测试 → 编译目标 kernel 并生成可安装算子包 → 安装到新的本轮前缀。具体 host 上下文、布局及包内容检查遵循参考文件“构建与入包”，通用实现沿用已加载模板。

安装后立即保存文件清单和 SHA-256；禁止用未入包的目标算子文件补漏。交付树、staging 和包中不含 `.pyc`/`__pycache__`，不复用目标算子的旧生成、对象或打包缓存。

### 6. 真机调用并验收

按所选通路的模板生成 C++ 用例，只使用本轮安装包：ACLNN 执行两段式调用并同步取回全部输出；GEIR 执行真实图调用并验证输出推导。参考文件“真机与离线证据”规定 GEIR 隔离、执行器生命周期和目标二进制命中检查。

用已加载精度 Skill 的进程外检查器验收原始输出，覆盖代表性、边界和每次只违反一项契约的非法输入。确定性功能及非法用例逐项通过；随机统计精度采用该 Skill 规定的验收单位和阈值，不以总体通过率掩盖功能失败。

为本轮交付件保留一个可重复执行的验收入口，串联上述实际命令和检查器，不复制第二套判定逻辑。执行前列明通路、阶段和预期用例；每次运行使用新输出目录，重新采集证据及运行前后清单，逐项关联命令、退出码、日志、输入与产物。调用/同步失败时不继续精度比对；未执行、证据缺失、文件大小不符或检查异常均不通过，最终汇总由实际检查生成。

在独立临时副本中注入缺失/截断输出、超限误差、缺失执行证据和错误调用标识，复用正常验收入口的同一检查路径，逐项确认非零退出且错误与注入项匹配；不得重新生成或覆盖被破坏的证据。

## 修复与交付

接入错误按原始错误最小修复，并重跑受影响阶段和最终验收；不放宽契约来绕过构建问题。kernel 或其本地辅助文件改动（包括改名）使旧映射、共享头、对象和 staging 失效，须从真实 codegen、最终映射、JIT 对比和 configure 重新验证；最终 kernel 及本地辅助文件与 staging 中对应文件的 SHA-256 须逐项相同。

只有改造前后 JIT、host 真执行、干净构建/独立安装、所选通路真机调用、目标二进制实际执行、精度和非法用例全部通过，才声明交付完成。任何必需通路失败均继续按上述边界处理，不静默跳过或手改结果为通过。

最终交付源码、契约、安装包、验收入口及原始证据；报告其路径、关键命令/退出码、实际用例和覆盖缺口、精度指标、目标执行证据与依赖版本。失败则明确首个未通过阶段及最小下一步。单个算子的通过不代表所有算子或全部输入范围均已验证。
