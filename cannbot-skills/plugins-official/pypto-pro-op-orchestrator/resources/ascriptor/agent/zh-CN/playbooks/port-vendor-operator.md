# 移植厂商算子

你手里是一个厂商 C++ 算子——AscendC 源码、host tiling 函数、infershape——目标是一个 Ascriptor
kernel，通常还在一个上游声明不支持的设备族上。先读一次[通用语言](../common-language.md)，再读本页，
然后围绕最终的代码路径做[飞行前检查](../references/authoring-preflight.md)。

这不是[迁移](migrate.md)（搬运已经在本工作区里的项目），也不是[导入](import-pypto-pro.md)
（把 PyPTO Pro 源码转成 Lowered IR）。它是[编写](author.md)，只是多了一份作为证据的上游实现；
而那一页没覆盖的工作在两头：第一行 DSL 之前，和第一次跑对之后。

<a id="source-only-handoff"></a>
## 仅源用例的交接

新建 A5 PyPTO-Pro 任务若仅要求源用例功能/精度验证，且已有官方 AscendC 源码（通常来自 A2/A3）、
host/tiling/infershape 和可运行的源用例，显式设置 `workflow_mode=source_ascendc_case`。
读取已安装的 `pypto-pro-scriptor-develop` Skill，再沿其中的
`references/ascendc-source-functional-precision.md` 链接执行；OpenCode 安装位置是
`$CANNBOT_CONFIG_ROOT/skills/pypto-pro-scriptor-develop/references/ascendc-source-functional-precision.md`。
Skill 不可用时报告资源缺口，不猜路径。

先还原并冻结 `SOURCE_CASE_CONTRACT.json` 和 `SOURCE_MAPPING.json`，然后由
`pypto-pro-scriptor-develop` 编写 A5 DSL、`pypto-pro-scriptor-verify` 独立验收真实 NPU 结果。
不调用要求冻结 `DESIGN`、`DESIGN_BINDINGS` 和 Module 合同的 `pypto-pro-op-develop`；
缺源语义或可运行用例是输入缺口，不能编造 formal 合同。

未提供 case 矩阵时只声明单用例覆盖，并留下 `FUNCTIONAL_RESULT.json`、`PRECISION_RESULT.json`、
`RUN_MANIFEST.json` 和 `ISSUES.md`。已有 formal Scriptor 状态/合同或完整 Scriptor/优化请求仍走原入口；
本路径不推进 formal 状态，也不替代其验收、交付或性能门禁。另行要求的性能工作保留为未完成项，
性能结果不能代替缺失的功能或精度证据。

## 1. 固定快照，写明目标，读支持表

把上游修订号、每个文件完整的 SHA-256 和实际 UTC 读取时间记进[迁移记录](../../templates/migration-record.md)。
上游是只读证据：它不能成为运行时导入，也不能提供参考实现。

**写明交付的后端和 launcher，并且把它和对照后端分开。** 一次移植交付在一个后端上——A5 通常是
PyPTO-Pro，用 `compile_kernel(entry, backend="pypto_pro")` emit、用 `OpExec(..., launcher="pypto")`
运行。CCE 和 PTO ISA 是**对照**：它们用来裁定失败，以及抓出只有某一个后端能打印的形式。
CCE 通过从来不是交付；一个在 CCE 下能跑、在交付后端下不能跑的用例是未决项，不是绿的。

先读上游自己的产品支持表。当它把你的目标标成不支持时，就**没有上游实现可以对照**——那块芯片上既没有
正确性 oracle，也没有性能基线。剩下的只有数学语义，以及上游在它确实支持的设备上跑起来（第 9 步）。

## 2. 从三个来源还原语义

一个来源不够，而且它们的失效方式各不相同：

| 来源 | 只有它能告诉你的 |
|---|---|
| 文档 | 公式、dtype，以及界定输入域的约束清单 |
| **infershape** | 输出形状——以及它是否依赖输入的*数值*而非形状 |
| **kernel 主体** | 算术顺序、累加位宽和舍入模式 |

三者冲突时以 kernel 为准，那是实际发布的东西；把冲突记下来，不要默默选一个。算术上有两处是可观测的，
而且任何文档都不写：

- **舍入模式。** AscendC 的 `CAST_ROUND` 把中间值向远离零的方向舍入，而 `torch.Tensor.to` 舍入到
  偶数。对应物是 `RoundMode.AWAY_FROM_ZERO`；边界的其余部分由[精度](../references/precision.md)管。
- **归约顺序。** fp32 加法不满足结合律，所以树形折叠和串行链的末位不同，任何落在舍入边界附近的结果
  都会移动。从 kernel 主体里把归约读出来，不要想当然地当成一个求和。

两者都只在少数元素上差约一个 ULP——而这恰好就是一个"宽到能通过"的容差会吸收掉的量级。把 reference
的目标定在逐位相等，两者才都藏不住。

出口是一份从不 import ascriptor 的 torch reference，以及一个对上游不接受的每一种情形都 raise 的
`domain()`。

<a id="domain"></a>
## 3. 声明输入域，然后覆盖它的角落

上游的约束清单就是你继承下来的域，`domain()` 是它变成可执行的地方。接着用例必须够到这个域的**角落**，
因为一份只采样中间的用例清单会全部通过，然后交付一个在约束允许的形状上直接 raise 的 kernel。
有三类角落默认会被漏掉：

- **每条约束的极值，尤其是最大值。** 那是 tiling 方案放不下的地方，而到交付时才发现意味着要重推
  数据流，而不是把某个数字改大。实测一次：域里最大的那个角落在第一版方案下根本放不下，关上它靠的是
  第二种分组形状，不是更大的预算。
- **某个数值走的代码路径，不等于这个数值本身。** 够到一条约束的极值，不等于够到这个极值所走的那条
  路径：同一次移植里，最大的那个维度被 tiling 分到了**窄**的那条分支，于是**宽**的那条——所有更小的
  形状都走它——一个用例也没有，而且是错的。在 tiling 做出选择之后，要问每个用例走的是哪条分支、
  有没有哪条分支一个用例都没有。
- **工作划分的边缘**：工作项少于核数、某一组不满、某个 tile 的有效宽度不是整数个寄存器。
- **数值而不只是形状**：一个完全不产出输出的输入、一个参差不齐的 batch、仍能产出一行的最短序列。

先拿上游自己的单元测试和样例里的形状——它们是白给的，而且代表了作者认为有代表性的东西——再补上它们
漏掉的角落。每个用例用一行说清楚：只有它覆盖了什么。

## 4. 把语义和"那块芯片的实现"分开

在写任何 DSL 之前先列两列表。每一行的判据是：换一块芯片它还成不成立。流式重叠状态机、UB 驻留方案、
32 字节 block 广播技巧、逐核 tiling 表，都是实现；公式、cast 边界、归约顺序和输出域是语义。
**不要逐行转译。**

允许的 host 工作以上游 host 已经做的为界。当它的 tiling 函数读取某个输入的数值来算偏移时，在 host
上推导同样的偏移是与上游对齐，而不是抄近路——而且这能把一个数据依赖量彻底挡在设备之外。越过这条界的
任何东西都是另一项约定，要连同理由写进[编写契约](../../templates/authoring-contract.md)。

## 5. 面向目标重新推导

四个问题，写代码之前回答，并用 [roofline](../references/roofline.md) 估价：

1. 用哪些计算单元。上游的选择反映的是它那块芯片，不是你这块；一个纯向量算子跑在 cube 闲置的部件上
   值得比一比，反过来也一样。
2. 核划分和 grid，对着这张卡的实际核数。
3. 数据依赖怎么消解——对 PyPTO-Pro 这是硬约束，见第 7 步。
4. 上游最复杂的那套机器到底买到了什么。拿上游自己的测试覆盖的用例去核对：一套只为某个参数区间存在、
   而那些用例从不进入该区间的机器，是这次移植不欠的。

## 6. 写 kernel 之前先探原语

一段只把每个不熟悉的机制在一个极小形状上各跑一次、过 emit 和 `sim` 的脚本，只花几分钟，就能把所有
意外提前到设计之前，而不是塞进一个写完的 kernel 里。留着它；后面出问题就对着它诊断。

<a id="emit-gate"></a>
## 7. 在设计之上盖任何东西之前先 emit

`compile_kernel(entry, backend=...)` 只要几秒，不需要卡，也不需要厂商工具链——
[那一页的第一条规矩](../references/pypto-pro.md#emit-first)。`PyptoGap` 会写明它的 owner，
而 owner 决定下一步：`ours` 是合同，不要绕；`upstream` 在它指出的源位置上报；`unmapped` 在有人核实
之前两者都不是。

这份合同里有三条会先于其它一切撞到移植：

- **tile 的分配维度必须是编译期的。** 运行时标量可以是地址或循环次数，不能是 extent。从 metadata
  张量里读一个几何字段、再按它驻留那么多行，是被设计性拒绝的——见
  [RFC 0013](../../../library/docs/rfc/0013-pypto-native-synchronization.md)。
  已绑定的标量参数不算运行时值：后端按每组取值特化。
- **往更宽的 tile 里做部分传输会叠两层 validshape**，没有拼法。整寄存器访问需要的余量要放在
  **多出来的一行**里，而不是多出来的列里；并且让 tiling 选得每组宽度都是同一个常量。
- `break` 和 `continue` 在打印器里没有行；改成用 `if` 包住循环体。

然后在三个后端上都确认这个表面，好让只有其中一个能打印的形式现在就暴露，而不是到交付时。

**emit 干净不等于能编译。** 厂商工具链看到的是 emitter 写出来的东西，一个合法但过大的形式会在那里
失败：展开的调度变成直线代码会溢出（实测一次：35 个 vector slot 对 6144 字节的 VF 栈，而同样的算术
写成小的设备循环轻松放下）。优先用"对一个静态容器里的编译期参数做循环"——步长保持常量，工作却不被
展开，也不会引入那个会拉进补丁依赖的设备侧除法。

## 8. 走证据阶梯，各级分开

先 `sim`，再 `pipesim`，再**用交付后端**上卡，遵循[硬件优先](../runtime-and-maintenance.md#hardware-first)
和[每一步在哪里跑](../runtime-and-maintenance.md#where-each-step-runs)的安排。源码生成、厂商编译和
设备执行是三项不同的主张，[证据表](../common-language.md#evidence)负责把它们分开。目标定在逐位相等：
移植是要复现一个算子，所以一个宽到能盖住舍入模式的容差，就已经盖住了一个。

**模拟器并不建模每一种冒险，后端生成的同步也不。** 有两种只有卡能看见：

- `@vf` 内部对 UB 的 store，没有 `vf_barrier(VfPipe.STORE, VfPipe.LOAD)` 就对后面的 load 不可见。
  一个把中间值落到 UB 再读回来的 kernel 在 `sim` 和 `pipesim` 下全部用例通过，在卡上全部用例错。
- 软件流水的预取如果越过循环末尾还在跑，它就是**一次没有读者的写**——而下一条流水的 prologue 是对
  同一个缓冲区的第二次写。生成的锁对**存在的**每一条依赖都是正确的；一个中间没有读者的写后写不是
  依赖。卡上是那次陈旧的传输赢了，于是第一组之后每一组的第一行输出，都是用上一组的列算出来的。
  **给收尾加护栏**：只在还有迭代会消费它时才预取。

当卡和两个模拟器都不一致时，先跑对照后端再去怪交付后端。上面第二种情形里 CCE 以同样的方式失败，
这正是"缺陷是我们自己的"的判据。

把同样的用例在同一张卡上再过一遍对照后端。只有当 CCE 通过同一个用例时，PyPTO-Pro 的失败才算移植
缺陷；而单一后端曾经藏住过一个静默的错误答案——但对照是诊断，不是交付。最后做
[交付同步政策](../runtime-and-maintenance.md#sync-closeout)，只报告实际请求并验证的模式。

<a id="oracle"></a>
## 9. 上游 oracle：当存在一张能跑它的卡

可选，在上游支持的部件你够得着时值得做一遍：在那里把厂商算子跑起来，拿它的真实输出去对第 2 步的
reference。先查已安装的 CANN——当算子已经在 `libopapi.so` 里或被厂商的 torch 扩展绑定时，根本不需要编。

这把"我们把源码读对了"从推理变成证据，而且这是唯一能够到任何文档都没写的语义的检查。实测一次：
reference 在六个用例中对上五个，第六个在 9216 个元素里差了 4 个，原因正是第 2 步的归约顺序——硬件
以下的每一级都一致通过，因为 kernel 和它所对照的 reference 犯了同一个错。**这里的不一致是关于你的
阅读的发现，不是厂商的缺陷**：把有差异的元素用几种方式分别重算，让算术说出厂商实现的是哪一种读法，
然后再改任何东西。

**只传代码。** 把 reference 和种子送过去，在那台机器上生成输入和厂商输出、在那里比对，带回来
的是修正后的 reference 和数字——绝不传输入或输出张量。理由就是
[运行你正在写的东西](../references/development-execution.md)里的那些：带种子的生成器跨机器不是逐字节
相同的，而这些数据存在的唯一目的就是和它自己比。

<a id="fast-enough"></a>
## 10. 让它足够快，并说清楚这是对着什么测的

一次复现了算术、却只跑出这块芯片零头能力的移植，只做了一半。[优化](optimize.md)负责方法；
有四件事是移植特有的。

**可能根本没有基线，那就说清楚有什么。** 当上游不支持你的目标时，没有厂商数字可比。剩下的是
kernel 实际请求的字节所对应的访存下界——见 [roofline](../references/roofline.md)，带宽假设由 library
拥有——加上这次移植自己在同一张卡上的前后对比。把下界当作敏感性场景报出来，绝不要当成实测的 HBM 效率。

**用 profiler 测，不要用 harness 测。** 授权路径的 `OpExec` 往返实测约 7.6 秒一次发射，而且对
0.01 MB 的用例和 2.9 MB 的用例**完全相同**：host 墙钟时间对 kernel 一无所述。
`ASCRIPTOR_PROFILE=1 ASCRIPTOR_REPEAT=N` 会把运行包起来，`ascriptor.runtime.perf` 读设备侧的
`Task Duration(us)`；配方在 [library 的 perf 页](../../../library/docs/perf.md)。

**把工作集放到 L2 之上，否则你测的是 L2。** 某块 A5 部件的 L2 是 112 MiB（平台配置里的 `l2_size`），
而寻常的 demo 形状能在里面放好几份。实测：输入 302 MB 时，第一次被 profile 的发射和之后那些的中位数
相差 1% 以内，这个数才是关于 HBM 的；输入 2.8 MB 时两者根本分不出来，比较的对象完全是另一级存储。
把第一次发射和之后那些分开报——它们的比值就是这种访存模式下 L2 值多少钱。

**动代码之前先看发射宽度，并让测量来挑该做什么。** 实测一次：交付的 `block_dim` 是 8，而这张卡有
28 个 block 是这个 kernel 填得满的，把它提上去就是 3.48 倍——一个发射参数而已。接着是逐 pipe 占用
指出了下一步：没有任何一条超过 0.53，说明它是依赖受限而不是管道受限，下一个 token 的载入根本没有和
当前 token 的算术重叠；把它做成双缓冲是 1.92 倍，两条管道随之到 0.89–0.99。而看起来最该优化的
"重叠窗口重读"测下来是免费的：更宽的形状请求了 1.91 倍的字节，只多花 1.24 倍的时间，唯一字节数还
完全相同，因为被重读的行还在 L2 里，所以那套本来要省掉这些字节的方案根本没有写。
一个被测量从计划里删掉的优化，和一个被测量证明该做的一样值钱——而且**一次流水化改动会带来一项新的
正确性义务**，所以它要重新过第 8 步，而不是凭加速比就交付。

## 11. 落地

四文件 demo 文件夹及其规则见 [kernels 契约](../../../kernels/AGENTS.md)；
[准入](../references/development-execution.md#admission)说明什么时候写另外三个文件。
`metadata.json` 里没有 provenance 字段——上游修订号和手改内容写在 `kernel.py` 顶部的注释里，处置表留在
任务的 `tmp/<task>/`。后端拒绝记在那个 demo `main.py` 里的 `# pypto_pro:` 注释中，别处不记。

报告时写明交付后端、用例覆盖了[输入域](#domain)的哪些角落、第 8 步各级分开的结论，以及
[第 10 步](#fast-enough)的测量连同它对着什么测。一个你主动保留的限制，要连同**让它成为一个选择的那次
测量**一起写进 `do_not_copy_when`；一个你没测过的限制是未决项，不是已记录项。
