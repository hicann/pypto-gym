# cce backend: what is printed and what is a gap

Generated by `tools/cce_support.py` (checked by `tests/backends/test_cce.py`); the opcode tables come from the
registry and the printer, the conditions from the printer's gap sites. A gap is a `CceGap` error naming the op
and its location (D-039), never guessed code. An example that hits a documented gap records the located
diagnosis as a comment beside the code it refuses; a measurement of it records a `gap` row in its receipt.

## Opcodes

Lowered-level opcodes in the registry: 282; printed for every function kind they
allow: **281**; a5 opcodes without a printer: **1**; tensor-list opcodes: **0**;
opcodes of the a2 family only (the c220 backend of M9, not an a5 instruction): **0**.

### a5 opcodes without a printer (gaps)

| opcode | kinds | what it is |
|---|---|---|
| `vec.topk_radix` | kernel | radix top-k |

`vec.topk_radix` is AscendC's high-level `TopK` library (a `LocalTensor` API with host-computed tiling), not a
c310 instruction: the cce backend keeps it a gap. D-047 parked it in the ascendc backend (M6); M6 is the pto_isa
backend since D-168 and the AscendC framework backend is not planned, so it stays an unowned cce gap. Every
other a5 opcode has a printer and a corpus or sample kernel behind it (D-045).

The public [radix_topk composite](api/sorting.md#register-radix-selection)
does not use this legacy opcode. Its frontend compiles a complete register
algorithm into existing VF operations, which the ordinary backend prints.

### a2-family opcodes (not a5)



## Conditions that still report a gap

| where | condition |
|---|---|
| scalar.sqrt | c310 nonnegative f32/f16/bf16 ordinary scalars and separate SIMT f32; BF16 uses explicit scalar conversion lowering; integer scalars have no CCE spelling |
| scalar.min / scalar.max | f32 prints Pro's `max((float)(a), (float)(b))` (RFC-0001 §6.16); a @vf cannot hold it on A5 and @simt has no measured spelling |
| cf.call | a vf function takes UB / GM windows and scalars; other window spaces cannot be passed |
| core.clean_dcache | needs a GM window in `dst` |
| dma.gm_to_ub.pad | an explicit pad value (`pad=`) fills the destination's 32-byte alignment tail through the `set_mov_pad_val` SPR, where AscendC's own DataCopyPadGm2UBImpl puts it; the SPR takes the value's BIT PATTERN, so the printer bitcasts it and only a LITERAL is reachable, and a 64-bit pad must be zero (AscendC asserts that for b64 on this device). Without a `pad` the tail keeps whatever the transfer found there. `dma.ub_to_gm.pad` has no pad value at all — the hardware has none on the way out (D-220) |
| dma.l0c_to_gm.* / dma.l0c_to_ub | atomic fixpipe stores print on c220 only (the `SetAtomic*` bracket on the AIC, mapping B.13); the c310 fixpipe API has no atomic mode (CANN's dav_c310 implementation carries none) — there, accumulate through UB and an atomic GM store (`atomic.begin`). A UB destination takes no atomic on either arch |
| dma.l1_to_l0.mx | needs the scale window in `src_mx` |
| dma.l1_to_l0.img2col | needs h, w, c, kh, kw, k_ext, m_ext |
| kernel parameters | any non-tensor, non-list, non-scalar parameter cannot be passed from the host (a `gmlist` is an input or an output: the aclnn DYNAMIC forms, D-048 / D-060) |
| mem.alloc inside @vf / @simt | slot buffers and allocations are kernel-level; a vf function receives windows |
| cf.for inside @vf | counts upwards on a uint16_t induction variable: a literal step must be positive, a scalar step is taken as positive |
| vf.reg | two-register groups support i64/u64/c32/c64 (D-229); other grouped dtypes are rejected by the frontend/verifier. Complex32 groups support normal loads/stores, copy/dup/select and add/sub/mul/div/adds/muls; cross-width group reinterpret and other group operations report a located gap |
| vf.load_cont / vf.store_cont / *_interleave | only the listed distribution modes; the 64-bit forms take plain vlds / vsts |
| vf.load_unalign / vf.store_unalign | post-updating loads need a zero offset; stores need a count and a zero offset |
| vf.gather_copy / vf.scatter_copy / vf.gatherb | a 64-bit index register contributes its low halves (`.val[0]`) as the element index; 64-bit gatherb data is the native single-register block gather; 64-bit scatter data is one 32-bit scatter of the interleaved halves with (2 i, 2 i + 1) indices, unmasked (D-050); two-register scatter uses the compiler's full-width masked form (D-229) |
| vf.* on 64-bit registers | the compiler header's two-register (vector_2xvl_*) forms: add / sub / mul / div / max / min / and / or / xor / not / neg / abs / shifts (32-bit amounts) / adds / muls / maxs / mins / cadd / cmax / cmin / sel / dup / cmp / cvt / lds / sts / gather2, and the printed sequences abssub, muladddst, muldstadd, axpy, gatherb, scatter (D-049, D-050, D-229); integer floor remainder and signed int64 arange are supported (the ramp's full-width base and decreasing order lower through desugar). Other 64-bit forms (exp / ln / sqrt / relu / prelu / lrelu / cgadd …) report a gap; n=1 has 32 logical lanes/256-byte transfers (D-050), n=2 has 64 lanes/512-byte transfers (D-229) |
| vf.* on complex registers | add / sub / mul / div / copy / load / store: the parts are the halves of the carrier register (c64: the fp32 halves of the 2xvl load; c32: add / sub on fp16 parts deinterleaved out of the packed lanes, mul / div in fp32 widened straight from the lanes and rounded once back, unmasked); other ops report a gap |
| vf.cast | `arch/c310.CAST_SHAPES` mirrors the vendor's own Cast API matrix for Ascend 950PR/950DT (D-218, and `tests/product/c310_cast_matrix.json` holds it; `tests/product/test_api_cast_matrix.py` compares the two). Not in the matrix, so gaps: unsigned <-> float, narrowing to int8, and the mixed-sign widenings (u8 -> i16, u16 -> i32, i8 -> u16) — reach them through the signed or the wider type. `e8m0 <-> bf16` IS in the matrix and is still a gap for a different reason, an upstream one: CANN declares the vcvt for __NPU_ARCH__ 9201/9202 only, and its builtin reports `does not support the given target feature` inside the op project's device build. Also gaps: a rounding mode the instruction does not admit (`arch/c310.CAST_ROUNDS`, now the doc's per-pair lists) and ANY merging cast — c310 has none, every row of the matrix is MaskMergeMode::ZEROING (D-051, D-218) |
| vf.mask_update | needs a scalar counter, not a literal: plt decrements a cell in place and a copy of any other value |
| vf.movp | no b8 form |
| vf.mem_bar | only the (src, dst) pipe pairs of `arch/c310.MEM_BAR` |
| simt.atomic | add / sub / max / min / exch / cas on every SIMT element type, and / or / xor on 32- and 64-bit integers (the c310 atomicAnd / atomicOr / atomicXOr builtins); the old value comes back for 32-bit types on UB and 32- / 64-bit on GM |
| vec.set_mask_count / vec.set_mask_counter | printed for c220 only. Counter mode is that backend's D-062 bracket around a counted tensor-level op; c310's vector unit is register-level and has NO operation whose extent the mode would govern -- an op's extent is the register width, the repeat count and an explicit MaskReg, and the mask SPR is a carrier a @vf reads with move_mask_spr rather than something that gates a store (board-measured: `tools/diag/probes/mask_counter_mode.py`). ## Types

Scalar / tensor dtypes with a C spelling: `b1`, `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, `f16`, `bf16`, `f32`, `e4m3`, `e5m2`, `hif8`, `e8m0`, `fp4_e2m1`, `fp4_e1m2`, `c32`, `c64`, `i4`.
Vector register dtypes: `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, `f16`, `bf16`, `f32`, `e4m3`, `e5m2`, `hif8`, `e8m0`, `i4`, `fp4_e2m1`, `fp4_e1m2`, `c32`, `c64`.
Complex registers (`c32` / `c64`) travel in their bit-pattern carriers (`vector_u32`, `vector_2xvl_u64`); add / sub /
mul / div / copy / load / store are printed on the (re, im) parts (D-049), other complex ops report a gap.

## Launchers

| launcher | what runs |
|---|---|
| `sim` | the interpreter (`backends/sim`), no toolchain |
| `aclnn` | the CANN custom-op project + host harness on a card (default) |
| `cannsim` | the same package under `cannsim record` (local CANN 9.0) |
| `board` | the same on this machine's assigned card, using a local `boards.json` entry |
| `direct` | not in M5 (the non-aclnn launcher of the old repository) |

## Not in M5

Complex and 64-bit VF sequences beyond the two-register forms, `vec.topk_radix`,
the direct launcher, batch bundles of many cases per transfer, the c220
tables (M9).
