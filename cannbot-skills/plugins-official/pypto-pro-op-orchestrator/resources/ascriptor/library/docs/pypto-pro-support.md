# pypto_pro backend: what is printed and what is a gap

Generated by `tools/pypto_support.py` (checked by `tests/backends/test_pypto_support.py`).
The tables are read out of the printer's own dispatch in `ascriptor/backends/pypto_pro/emit.py`,
not maintained by hand: a hand-maintained table drifts in both directions, and both have
happened here — eight opcodes the printer handled and the list did not declare (`262d6d6`),
four the coverage table claimed and nothing printed (`44bbfd3`).

[The coverage survey](pypto-pro-coverage.md) is dated investigation history and the
[mapping reference](pypto-pro-mapping.md) describes the emitted spellings; this file is
neither. It answers one question: for each opcode, is there a line?

Lowered-level opcodes in the registry: 282; printed: **213**; without a line: **27**;
other devices: **42**. The backend declares 213 opcodes in
`capabilities()`, and 6 more are dispatched only to be refused with a located gap.

A printed opcode may still report a gap for particular operands, dtypes or attributes;
those conditions live next to the code that raises them, and `PyptoGap` always carries the
op id and the source location.

## Dispatched, and refused there

These reach a branch of their own, which raises a located gap rather than
falling through to the generic one. The message is the useful part.

* `scalar.abs`
* `scalar.sqrt`
* `simt.ffs`
* `simt.popc`
* `vec.mergesort4`
* `vf.mod`
