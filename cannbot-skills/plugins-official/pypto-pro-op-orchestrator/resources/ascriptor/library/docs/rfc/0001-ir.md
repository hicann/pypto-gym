# RFC-0001: The ascriptor IR

Status: implemented in M1 (`ascriptor/ir/`), amended to match; still open for review. §16 lists what exists.
Decisions this RFC depends on: D-002, D-005, D-007, D-014, D-015 (`docs/decisions.md`).

## 1. Purpose and requirements

The IR is the product. The frontend produces it, passes rewrite it, backends consume it, the
simulator interprets it, and the maintainer reads it. Everything the old repository kept in
live Python objects, C++ expression strings, module globals and text-level passes must be
expressible here, or it cannot be lowered at all.

| # | Requirement | Consequence |
|---|---|---|
| R1 | Data, not objects | Every operand and attribute is a plain value: name, literal, type, list of these. No callables, no host objects, no rendered code. |
| R2 | Two levels | **Surface IR** is what the frontend emits; **Lowered IR** is what every backend reads. Same grammar, different invariants (§10). |
| R3 | Round trip | `parse(print(m)) == m` for both levels, text and JSON. Lowered IR on disk (`.lowered.ascrip`) is the serialisation boundary between the compiler and any backend, including third-party ones. |
| R4 | Registry | One op registry (§6) is the only source of truth for opcodes. Verifier, autosync sets, sim routing, capability matrices and docs derive from it. |
| R5 | Passes are IR → IR | No pass reads source text or emitted code. |
| R6 | Backends are pure | `compile(module) -> Artifacts`; no process-global state, no environment reads. |
| R7 | Provenance | Every op has a stable id, a source location and an origin chain (§8). |
| R8 | No escape hatch | There is no op that carries opaque backend text (D-007). |

Non-goals for v1: an optimising middle-end (no scheduling, no register allocation beyond what
the DSL already states), multiple kernels per module, kernels calling kernels, dynamic
allocation of on-chip memory.

## 2. Two levels

| | Surface IR `surface/1` | Lowered IR `lowered/1` |
|---|---|---|
| Producer | frontend | pass pipeline |
| Device | named in the module; ops are the device-neutral spellings the DSL uses (`dma.copy`) | ops are device-specific selections (`dma.gm_to_l1.nd2nz`), one intrinsic each |
| Functions | one `kernel`, any number of `vf` / `simt` | kernel split into `.cube` / `.vec` sides; `vf` / `simt` unchanged |
| Pipe | absent | on every op |
| Sync | events named, no ids; `region.autosync` present | events have channel and id; all sync ops explicit, regions gone |
| Memory | allocations typed, no addresses | every allocation has `addr`; list-descriptor reads are explicit scalar loads |
| Shortcuts | `cube.matmul` etc. kept | expanded |

The pipeline between them (§12) is fixed; a backend may append backend-specific passes, which
must keep the module in `lowered/1`.

## 3. Module

```
module @matmul_float_mmad { device = "950", ir = "surface/1", mode = "mix",
                            source = "kernels/a5/matmul/matmul_float_mmad.py",
                            source_sha256 = "…", next_id = 41 }
  kernel @matmul_float_mmad_kernel(...) { ... } { ... }
  vf @cast_tile(...) { ... }
  simt @axpy(...) { ... }
```

Module attributes: `device` (device type, §14 profile), `ir` (level and major version),
`mode` (`mix` | `vec` | `cube`, the old `@kernel(mode=...)`), `source` / `source_sha256`
(provenance), `next_id` (op-id counter, §8). Unknown attributes are preserved by parser and
printer (§9.4).

Function kinds:

| kind | runs on | entry | may contain |
|---|---|---|---|
| `kernel` | both sides (Surface) / one side per split function (Lowered) | yes, exactly one per module | everything except register ops |
| `vf` | vec side, called from the kernel | no | register ops (`vf.*`, `mask.*`), scalar ops (on A5 no f32 min/max, §6.16), `cf.*`, UB loads/stores; no DMA, no cube |
| `simt` | vec side, launched from the kernel | no | `simt.*`, scalar ops, `cf.*`, GM/UB loads/stores |
| `func` (Lowered only) | one side, `side = cube \| vec` | one per side | lowered kernel ops for that side |

A function has parameters (`%name : type`), attributes and one block. Kernel attributes:
`outputs = [%z, ...]` (the parameters the DSL kernel returns; RFC-0002 §3), `block_dim`
(a launch expression over shape symbols, RFC-0002 §3.4), `workspace = [...]`, `crosscore = [...]`
(cross-core flag registrations), and in Lowered IR `side`.

## 4. Types

### 4.1 Scalar dtypes

Canonical IR spellings. The DSL keeps every existing `easyasc` name as an alias (D-008 #8);
the alias table is filled in M2 from the old `utils/datatype.py` and is not part of the IR.

| IR | bytes | notes |
|---|---|---|
| `b1` | 1 | boolean scalar |
| `i8` `u8` `i16` `u16` `i32` `u32` `i64` `u64` | 1–8 | integers |
| `f16` `bf16` `f32` | 2–4 | floating point |
| `e4m3` `e5m2` `hif8` | 1 | 8-bit floats |
| `fp4_e2m1` `fp4_e1m2` | ½ | packed two per byte; element counts must be even |

FP4's sign bit is preserved for finite inputs, including negative zero and
negative values that round to zero. Thus positive and negative zero encode as
nibbles0 and8. Packing retains the lower-index element in the low nibble.
M10-041 independently verifies every finite BF16 carrier for the A5 E1M2
nearest-even cast. That evidence does not qualify unmeasured cast modes on
hardware; public host-codec sign preservation applies to both FP4 formats.
| `e8m0` | 1 | scale type |
| `c32` `c64` | 4 / 8 | complex (a2 family only) |

Device availability per dtype is a registry fact (§6), not a type-system fact.

### 4.2 Dimensions

A dimension is one of: an integer literal; a **symbol** (identifier, declared by a kernel
parameter of scalar type or by a signature shape symbol, RFC-0002 §3.2); `?` (ragged, only
in `gmlist` member types); a **product** of literals and symbols (`M*K`, the only shape
expression allowed, D-014); or a scalar SSA value or cell in scope (`%n`). Value dimensions are allowed in local
allocations too — the DSL writes `Tensor(DT.half, [TILE_M, K], Position.L1)` with a runtime
`K` all over the corpus — so `addr_alloc` emits address arithmetic where a size is dynamic, the
capacity check proves only what is static, and a backend that needs compile-time tiles
(`pypto_pro`) reports a gap (D-018). A type that names a value is only meaningful where that
value is in scope; the verifier checks it. On-chip tensors (`l1`, `l0*`, `ub`, `bt`, and the
elements of `buf`) are **two-dimensional**, as `Tensor` / `DBuff` / `TBuff` / `QBuff` are in the
DSL; GM tensors have any rank. The rule is a verifier invariant (backends rely on it for
address arithmetic and NZ layout), and the frontend reports it at the DSL line as well.

### 4.3 Memory types

| type | meaning |
|---|---|
| `gm<T, [d0, d1, ...]>` | a global-memory tensor or view |
| `gmlist<T, [d0, ...]>` | a list of GM tensors sharing one member type; `?` marks per-member dims |
| `l1<T, [r, c], nz \| nd>` | L1 tile with layout |
| `l0a<T, [r, c]>` `l0b<T, [r, c]>` `l0c<T, [r, c]>` | L0 tiles (layout implied by position) |
| `ub<T, [d0, ...]>` | unified-buffer tensor, row-major |
| `bt<T, [n]>` | bias table |
| `buf<P, n>` | a slot buffer: `n` slots of local type `P` (the old `TBuff`); slots are taken with `mem.get_buf` |
| `ws<T, [d0, ...]>` | workspace (GM scratch owned by the launcher) |

A view has the same type family as its base; `mem.view` / `mem.slice` / `mem.reinterpret`
produce new values, never mutate. Lowered allocations carry `addr` (§10).

L0 matrix operands retain the IR coordinate order: L0A is `[M, K]` and
L0B is `[N, K]`. A backend whose Right tile is named `[K, N]` must transpose
the *coordinate description* exactly once, including a slice's extents and
origins and the selected slot's shape. This renaming does not transpose or
repack the stored values. A view must retain its parent's physical fractal
pitch; a smaller valid region alone does not make a rectangular view compact.
For byte-addressable L0B elements, with `C0 = 32 / element_bytes`, logical
element `(n, k)` is at element offset
`(k // C0) * align16(N_parent) * C0 + n * C0 + k % C0`.
Backend-specific restrictions on materializing such a view must be reported
at its operation/source location, rather than silently changing that mapping.

A register store's physical extent follows its distribution and active mask;
a shorter destination view does not implicitly mask the instruction. The
simulator must reject active distributed-store lanes outside the backing
allocation, including a normal full-register store from the last half-row of
a slot. It must not silently discard those lanes. In-range stores and explicit
half masks retain their instruction semantics (M10-057).

`vf.load_interleave` reads 2L register-width elements from its offset: element 2i enters lane i
of the first destination and 2i+1 lane i of the second. `vf.store_interleave` writes element 2i
from the first source and 2i+1 from the second for every lane: A5 wrote all pairs with empty,
prefix, compare and b16 predicates, so its mask has no effect and the whole footprint must be in
range. Both copy carrier bytes from a 32-byte-aligned start (I024).

`vf.load`/`vf.store` copy lane b*L+j, L = 32 / element bytes, at element `offset + b*N*L + j` for
`blk_stride` N (1 when absent), so N = 0 puts every block at block 0. Stores write active lanes in
lane order, the last one winning; loads zero inactive lanes, but at N other than 1 A5 reads block b
whole when any of its 32 physical predicate bits is set (I035).

Ordinary register/UB and DMA/UB transfers require a 32-byte-aligned UB
instruction start after composing the allocation, slot, view/reinterpret and
explicit offset. Multi-row DMA also requires each physical UB row start to
meet that alignment; logical valid columns do not define its row pitch. The
GM side of a GM/UB DMA has no corresponding 32-byte restriction: a GM source
or destination at byte offset 16 remains legal when its typed payload fits.
Functional and pipe simulation reject an actual unaligned UB access with its
operation/source location; executing it element-exactly with a hardware warning
is not acceptance.

The UB allocator owns `align32(logical_bytes)` bytes per independent slot.
Models retain that padding as physical backing while preserving the logical
tensor shape. A short aligned view, such as four FP32 values at the beginning
of a physical 64-value row, is legal. Padded DMA validates its complete
32-byte-rounded UB footprint before any write, including every burst and
the last padded block. It must neither clip that block nor borrow storage
from a neighboring allocation/slot. On A5, a `dma.gm_to_ub.pad` burst without
`pad` fills the rest of its last block with copies of its first element
(I038). An actual 16-byte row pitch remains
invalid for a multi-row ordinary transfer even if its first row is aligned.
Register distributions and active predicates retain their own consumed
element ranges; a short logical view supplies no implicit register mask.
Indexed gather/scatter also keep an aligned instruction base; their explicit
element indices retain the individual-address semantics of those operations.
An executed ordinary register/UB instruction requires that aligned base even
when every predicate lane is off. Predicates suppress the selected lane/block
effects and their range checks; they do not waive the instruction's base-address
precondition. This follows the separately stated alignment and masked-access
rules for [LoadAlign](https://asc.gitcode.com/api/SIMD-API/c_api/reg_compute/load/asc_loadalign.html),
[StoreAlign](https://asc.gitcode.com/api/SIMD-API/c_api/reg_compute/store/asc_storealign.html)
and [UB Gather](https://asc.gitcode.com/api/SIMD-API/c_api/reg_compute/ub_gather/asc_gather.html).

Scalar UB operations and VF scalar broadcast/first-element transfers
(`.single()`/`.single_value()`) use element alignment and access one element.
Explicit unaligned load/store chains retain their separate state, range and
final-flush contract below; they are not ordinary aligned transfers. A zero-burst
DMA performs no transfer and imposes no address alignment check. Unexecuted
instructions, including a zero-trip VF loop or an uncalled VF, are not checked.

The current logical simulator does not model arbitrary physical L0C pitch
remapping. Cube writes record their compact `align16(M)` fractal-column pitch.
A FIX transfer that reads a later computed N block using a different `M_src`
must report a located simulation gap before writing its destination, rather
than return the complete logical product as if the descriptors agreed. Matching
pitches and a single first N block remain valid. This diagnostic does not make
unused physical padding deterministic or reject that descriptor in CCE (M10-042).

Register reductions read all active source lanes before modifying an aliased
destination. In-place group add/min/max must not zero their source while
clearing inactive result lanes. Mask selection and each group's independent
32-byte extent are preserved (M10-043).

`vf.cmax/cmin` write the extremum of the active lanes to lane 0 and zero the other lanes;
`index = true` keeps the first active lane holding it in lane 1 as integer bits, as the bare
instruction does. `vf.cgmax/cgmin` write group g to lane g without index lanes. An empty
selection gives the dtype's lowest (max) or highest (min) value, and index 0; an empty group
sum is 0. An active NaN gives the all-ones positive NaN (A5 FP32 0x7FFFFFFF) and its first lane;
-0 orders below +0. A5 measured these on FP32/INT32; the model applies them to every width
(I025).

### 4.4 Register and control types (vf / simt / sync)

| type | meaning |
|---|---|
| `reg<T, n>` | a vector register of `T`, `n` ∈ {1, 2} (the old `Reg` carriers) |
| `mask<b8 \| b16 \| b32 \| b64[, n]>` | predicate register by logical lane width and register count; omitted `n` means 1 |
| `unalignreg<load \| store>` | the 32-byte alignment shift register of an unaligned load or store chain; the role must match the chain's ops (AscendC `UnalignRegForLoad` / `UnalignRegForStore`, one CCE `vector_align`) |
| `cell<T>` | a mutable scalar variable (§5.2) |
| `event<depth>` | Surface: a same-side pipe event with `depth` ∈ 1..4 (old `SEvent/DEvent/TEvent/QEvent`); Lowered: `event<depth, set_pipe, wait_pipe, id>` |
| `flag` | a cross-core flag (Lowered: with id) |

Register groups (D-229): `reg<T, n>` contains `256 * n` logical bytes, with `n` in
{1, 2}. On c310, the two-register form supports `i64`, `u64`, `c64` and `c32`;
it is not an array of independent registers. `mask<bW, n>` has `256 * n * 8 / W`
logical predicates. Its count is preserved through text/JSON round trips and mask
expressions; the existing one-register spelling remains unchanged. A grouped
compute operation must not silently read a single-register operand or use a mask
with fewer logical lanes. Casts and real-valued complex abs may change the count
because they change element width; the number of accessible source lanes bounds
the conversion. Unsupported grouped operations report a located backend gap.

Indexed register-memory operations interpret each index according to its declared
integer signedness. Every active indexed access must lie within the accessible
allocation suffix after the view origin and explicit offset. The models reject
an invalid active index at its source location; Python negative-index wrapping
is never a memory-access semantic. A scatter checks the complete active index
set before writing. Masked-off indices are not accessed. Byte scatter retains
its physical lane mapping: index `k` selects source byte and predicate `2*k`
(M10-031, M10-037). Active scatter lanes may share a destination only with
identical payload bits. A5 leaves the surviving writer unspecified, so the
models reject differing duplicates with that index check (I015).
Block gather samples its predicate at UINT32 index lanes: physical bit `4*b`
selects block `b`, which is read whole from the byte offset in index lane `b`.
Unselected blocks are zero and not accessed. A5 runs measured b32 (lane `b`)
and b16 (lane `2*b`) predicates; a b64 predicate reaches odd blocks only
through unqualified fine bits (§5.1, I014).
Register `vf.gather` writes source lane `index` to each destination lane. With an
f32 or i32 source and i32 or u32 index (64 lanes), or an f16 source and u16 index
(128 lanes), it reads lane `index mod lanes` of the index bits as unsigned, as A5
`vselr` measured natively and through CCE. Other pairs need indices inside the
source lanes; the models reject the rest.

`vf.mod(dst, lhs, rhs)` is integer remainder with floor-division semantics (the
sign of a nonzero result follows the divisor). The c310 form supports matching
`i64` or `u64` registers, including groups. A zero divisor produces all-one bits;
the signed minimum divided by -1 has remainder zero. `vf.arange` on `i64` accepts
a full-width signed starting value and increases or decreases by one per lane.

## 5. Values and names

### 5.1 SSA values

Every result is a `%name` defined once. Names come from the Python source when there is one
(`%a_l1`), otherwise from the op (`%dma.3`); a name reused in source gets a suffix (`%x.1`).
Names are for readers; identity is the op id (§8). Uses must be dominated by definitions
within the structured block tree (§7): a value defined inside a region is not visible after
it, and the results of an op that owns regions (the induction value of `cf.for`) are visible
only inside those regions.

Predicate operations consume one physical 256-bit register. The logical lane
view selects one bit per effective element-width group; supported two-register
data groups use the same physical predicate register at their effective width.
Its physical payload must survive load/store, selection and Boolean routing;
the interpreter may not reconstruct the whole payload from logical lanes.
Masked comparison produces false in inactive logical lanes. Masked
NOT/AND/OR/XOR/MOV zero inactive physical predicate bits. Predicate/data
selection instead chooses between both sources for every destination position.

Predicate pack selects physical source bits 0,2,...,254 into the chosen
128-bit destination half and clears the other half. Unpack expands the chosen
half into physical even positions and clears odd positions. Interleave and
deinterleave route effective-width bit groups. Inputs, including execution
masks, are read before destination writes when operands alias (M10-051).
Measured raw routing covers b8/b16/b32. The separate b64 single-register ABI
and unobserved fine bits produced by compare/init/update remain explicitly
unqualified; current model conventions are not additional silicon evidence.

### 5.2 Mutable scalars are cells, not phis

The DSL's `Var` is a mutable scalar (`acc += 1` inside loops). The IR models it as a
**cell**: `%acc = scalar.cell : cell<i32> { init = 0 }`, written by `scalar.set(%acc, %v)`
and read by naming it as an operand of any scalar op (the read happens at the op). No phi
nodes, no block arguments.

Why: every code-generating backend prints C, where a cell is a variable and a phi would have
to be eliminated back into one; no planned pass needs scalar dataflow (autosync reasons about
buffers, DCE about side effects); and the printed IR stays one-to-one with the source. The
verifier forbids reading a cell before its first `scalar.set` on every path (`init` counts).

Loop induction values (`cf.for` results) and everything else are immutable SSA values.

A cell-to-cell assignment, including a cell's initializer, reads the source at
that operation and copies its value; it does not make the destination an alias
of the source cell. For example, `previous = current; current = current + 1`
must leave `previous` with the value before the increment, including at a loop
backedge. A backend that translates cells through an upstream SSA DSL must
preserve this snapshot when that DSL eliminates its loop arguments. Sequentially
updating a source loop argument before copying its old value into another
argument is incorrect. Generated variable names must not determine this behavior.

### 5.3 Literals

Integers (`42`, `-1`, `0x1000`), floats (`1.5`, `inf`, `nan`, always with a dtype context),
booleans (`true` / `false`), strings (`"…"`, for attributes only), enums (`nz`, `MTE2`,
bare identifiers in attribute position), lists (`[...]`), and value references (`%x`, `@f`).

## 6. The op registry

### 6.1 Entry

Every opcode is declared once, in Python (`ascriptor/ir/ops/*.py`), and exported with
`ascriptor ops --json`:

```python
op("dma.gm_to_l1.nd2nz", level="lowered", side="cube", pipe="MTE2",
   operands=(W("dst", "l1<T, *, nz>"), R("src", "gm<T, *>")),
   attrs=(A("M", "int|value", required=True), A("N", "int|value", required=True),
          A("M_dst", "int|value", required=True), A("N_src", "int|value", required=True)),
   legacy="gm_to_l1_nd2nz", effects=("memory",), doc="GM ND -> L1 NZ")
```

Entry fields (`OpSpec`): `name` (namespace-qualified), `level` (`surface` | `lowered` | `both`),
`kinds` (function kinds it may appear in), `side` (`cube` | `vec` | `any` — `any` means the
split pass decides), `pipe`, `devices` (`None` = all), operands with type patterns and
`read` / `write` / `readwrite` / `none` access (`none` for scalars, events and functions),
attributes with types (`int`, `float`, `bool`, `str`, `ident`, `value`, `list`, `any`, unions
such as `int|value`), defaults and `required`, results with patterns, `regions` (names), `terminator`,
`effects` (`memory`, `sync`, `debug`, `control`), `legacy` (the old instruction names this op
replaces) and `doc`.

Operands are positional and required. An **optional value input** — a predicate mask, a bias
tile — is an attribute of type `value` with its own pattern and access (`A("mask", "value",
pattern="mask<*>", access="read")`), so it is absent when unused and still visible to
autosync, which reads accesses from operands and value-attributes alike.

Type patterns are type spellings with variables: a capital letter in dtype position binds a
dtype (`T`), a lowercase identifier in dimension position binds a dimension (`r`), `*` matches
anything in its position, and the pseudo-spaces `local` / `l0` / `mem` match a family of memory
spaces; standalone `scalar` / `int` / `float` / `bool` match scalar types by class, `value`
matches any type. Variables are unified across all operands, value-attributes and results of one
op (`match()` in `registry.py`).

The `access` sets drive autosync (which buffers an op reads and writes) and DCE; the `pipe`
drives event insertion; `devices` drives `Capabilities` and early diagnostics.

### 6.3 SIMT FP32 integral rounding

`simt.round`, `simt.rint`, `simt.floor`, `simt.ceil` and `simt.trunc` return FP32
integral values, not integers. `round` selects nearest with half ties away from
zero; `rint` selects nearest with ties to even. `floor`, `ceil` and `trunc` round
toward negative infinity, positive infinity and zero respectively.

Their floating-point model preserves the input sign when the result is zero,
including an explicit `-0` input. Positive and negative infinity remain unchanged;
NaN remains NaN, without a NaN payload or sign guarantee. Finite results, infinities
and zero signs are tested by exact FP32 bits. A floating-point equality comparison
alone cannot distinguish the two zeros.

This clarifies the scalar rounding model for M10-013: converting a Python integer
zero back to FP32 loses the sign, and integer conversion rejects non-finite inputs.
Those host-language artifacts are not the floating rounding semantics. The
generated regression uses independent Torch operations and an explicit half-tie
correction. M10-054 subsequently observes A5 native builtins losing negative
zero and adapts that target behavior without changing these operation semantics.
The compatibility wrapper restores the input sign only when the native result's
magnitude bits are zero; every nonzero result is retained. `simt.fmod` has no
rounding step (§6.15).

### 6.4 Scalar memory access

`scalar.load` and `scalar.store` address one element in GM, a GM workspace or UB.
Kernel-level `Var.GetValueFrom` / `SetValueTo` use the first element of the supplied
view, including an unsliced tensor; an indexed view contributes its actual flat offset.
Loads convert to the destination scalar dtype and stores convert to the memory dtype.
L1 and L0 memory are not scalar-addressable through this API and must produce a located
diagnostic. A store has an observable memory effect and may not disappear merely because
no operation consumes a result value. IR accesses and the S pipe determine synchronization
with DMA; backend support is checked separately and an unimplemented space reports a gap.

M10-016 restores the documented UB path already implemented by the interpreter and CCE
wrapper. The previous GM-only operand pattern was a registry bug, not a reason to remove
the public UB scalar contract. Scalar memory methods remain kernel-level frontend operations.
`scalar <<= tensor_view` and `scalar >>= tensor_view` are the load/store operator spellings
of these methods and preserve the scalar cell. A scalar right-hand operand to `>>=` remains
an arithmetic right shift; operand types determine the operation (M10-019).

### 6.5 Scalar helper constant folding

Static scalar helpers preserve the operation selected by their operand types.
`var_div` with a floating operand performs floating division, including mixed integer/float
arguments; constant folding must not replace it with floor division. The existing integral
division path remains separate. Generated checks compare constant and cell-valued spellings
on finite floating inputs with nonzero denominators and on nonnegative integer dimensions
(M10-020).

`scalar.sqrt` produces its declared floating result type. Its model rounds the
result at the operation, including FP16/BF16 narrowing, even when lowering
eliminates a following cell. Cell materialization must not change numerical
results. The c310 spelling and qualified nonnegative input domain are recorded
in RFC-0007 and M10-053.

`scalar.abs` preserves its operand/result dtype and produces a nonnegative
magnitude. Floating negative zero becomes positive zero; either infinity
becomes positive infinity and NaN remains NaN (no payload guarantee). The
signed integer domain excludes the minimum value of the result dtype, whose
positive magnitude is not representable. Unsigned absolute value is identity.
These semantics also apply after cell elimination. A5 native scalar absolute
value covers i8/i16/i32/i64/f32; FP16 may widen through FP32 and narrow exactly.
An unsupported backend form must report a located gap, not substitute a tile
or VF operation for a kernel-level scalar instruction (M10-062).

### 6.6 Vector scalar operands

For A5 `vf.store_cont` with `mode=pack_b32` and a 16-bit source register,
destination element `i` receives source element `2*i` only when that source
lane's physical predicate bit is active. Inactive destinations retain their
previous bits. The store does not round a partial predicate to a 32-byte
block and does not compact holes in a sparse predicate. M10-064 records
matching CCE/PyPTO board controls for short prefixes and a sparse M3 mask.

A `vf.reg` declaration does not establish a portable hardware value before
its first write. The functional model seeds fresh registers with zero. A
backend whose API requires a producer before every register use may
materialize that seed in an explicit lowering pass, recording provenance.
It must preserve all defined writes, predicates and live loop-carried values;
a load/compute-defined register does not need an extra initialization.
Declaring a `vf.reinterpret` view is not a use of its source register: the view's
first use is, and it reads the register the view belongs to.

`vf.dup` reads a scalar cell's current value at execution time, including a counter
mutated by `vf.mask.update`. It must not pass the cell container to host tensor
operations. Register-source duplication remains a lane-zero broadcast with its
existing mask semantics (M10-022).

### 6.7 Atomic memory footprints

A GM DMA store with an `atomic` rider (`add`, `max` or `min`) is an atomic
read-modify-write of the destination. Its source reads remain ordinary reads.
Pipe traces retain this classification just as they do for supported SIMT
atomics: atomic/atomic overlap is permitted; overlap with an ordinary read or
write still requires ordering. The classification does not change numerical
execution order, floating accumulation tolerances or scheduling cost (M10-023).

### 6.8 Simulator print formatting

`debug.print` uses a static percent-format string plus resolved scalar/string
arguments. `kernel_print(fmt, *args)` preserves the supplied format;
`sim_print(*args)` lowers to space-separated `%s` fields, so literal braces and
percent characters inside its arguments remain text. The current CCE backend
prints diagnostic comments for these operations and does not promise vendor
printf or tensor-dump execution (M10-024).

### 6.9 Raw flags and scalar memory footprints

On A5, Lowered `sync.local_mutex_get/release` use an integer `id` (0..31),
explicit `pipe`, `side` and `mode=0`. Each AIC/AIV participant has a separate
namespace, initially free. A get waits for the preceding release of that ID
in scalar issue order; release completes after earlier work on its named pipe.
An executed section must acquire once and release on the same pipe; unmatched,
repeated or outstanding acquisitions fail model validation. IDs in traces are
immutable runtime snapshots. Cube pipes are S/M/MTE1/MTE2/FIX; vector pipes
are S/V/MTE2/MTE3. These are local buffer locks, not cross-core credits.
CCE/PTO emit explicit mode-zero get_buf/rls_buf; Pro re-emission requires manual
sync mode when the IR owns locks. Timing is modeled, not silicon calibrated.

Raw `sync.set_flag` / `sync.wait_flag` operations must name a supported
ordered channel: the source and the destination are two different pipes
of the side, S included on either end. The scalar pipe sets flags: Pro's
tile library emits `set_flag(PIPE_S, PIPE_MTE3, …)` before a store whose
address S computed, and on A5 four cross-core stores into one cache line
survive only when the publication pipe waits for the scalar pipe that
cleaned the line ([I012](../defects/I012-simulator-gm-cache-line-stores.md)).
Automatic event allocation still never sets a flag on S; the channel is
for source programs and imports that order the scalar pipe by hand. The
C220/C310 channel has eight flag IDs (0 through 7). A statically known
invalid ID or pipe pair must produce a source-located verifier error. A
dynamic ID must be an integer scalar; the model validates its runtime
value before recording the operation. Runtime raw IDs reserve the entire
channel during automatic event allocation unless their value is
statically known. The trace must
snapshot each executed ID, not retain a mutable scalar expression.
These rules close M10-045.e's accepted invalid raw-flag probes; they do not
increase event capacity or certify an invalid program by emitting it.

Scalar `scalar.load` / `scalar.store` accesses use the memory view's physical
origin plus the explicit scalar index and one element of the memory dtype.
Execution and pipe tracing must share this address calculation, reject
addresses outside the backing allocation and retain memory-space/core/slot
ownership. Trace granularity remains the model's declared access granularity;
the root memory operand's entire extent is not a scalar footprint. Disjoint
32-byte rows must not conflict merely because their scalar operations refer
to the same root buffer; actual overlaps must still be diagnosed (M10-045.c).

For A5 explicit FIX operations, known descriptor read/write ranges must fit
the backing allocation (one slot for a slot buffer), including the view's
physical byte origin. Source NZ addressing uses 16-column blocks and the
16-row-aligned M_src pitch. ND/DN destination addressing uses its declared
row/column stride; L1 NZ addressing uses its element-width column block.
Split-M/Split-N UB transfers check each destination sub-block separately.
An ND UB column subview retains its parent's physical row stride. For example,
the two `[16,128]` halves of an FP32 `[16,256]` allocation have 1024-byte row
strides and byte origins 0 and 512. Aligned origins do not make those windows
contiguous. A backend must preserve the parent pitch and logical valid extent,
including a rotating slot, or reject the transfer with its DSL source location.
PyPTO's native Tile slicing keeps that physical shape/stride and narrows only
the valid shape; it can therefore carry a FIX destination subview without a
new compact allocation. The generated FIX must retain its declared Vector
split mode and must not turn the window into a packed `[16,128]` alias.
An explicit `N_dst` is the instruction's actual destination row stride, even
when it differs from the logical view's parent stride. When its footprint is
valid, functional writes, bounds checks and pipe accesses use the same composed
view origin, `N_dst` and Vector split. A model must not check one physical
descriptor but execute a different logical-slice copy. Such an explicit
descriptor does not change the parent tensor's layout for later consumers.
Local allocation padding is included; a view extent is not an allocation
bound. A large M_src is valid when only the first N block is touched and
the resulting range fits. Zero-size transfers have no byte footprint.
The verifier rejects only proven static violations; the model applies the
same range rules to concrete dynamic descriptors before any destination
write. Packed/low-precision NZ destination forms without a qualified byte
rule retain their existing separate limitations rather than an invented
bound. This is descriptor validation (M10-045.f), separate from the
producer-layout mismatch diagnostic and from arbitrary layout emulation.

A backend's source FIX carrier must also preserve the descriptor's physical
M_src pitch. Accepting a runtime M_src while emitting an unchanged static Tile
pitch is not a valid implementation of the descriptor. A backend unable to
express that pitch must reject the dynamic form at the FIX's source location,
even when its destination range and logical valid shape otherwise fit. Static
branches with matching source carriers may express the supported cases.

### 6.10 Integer division and remainder

Typed integer `scalar.div` and `scalar.mod` have a `rounding` attribute:
`floor` (the default) or `trunc`. Integer `/`, `//`, `%`, `var_div` and
`var_mod` use floor semantics; helper calls accept `rounding="trunc"` for
an explicit quotient toward zero and a remainder with the dividend's sign.
Both modes satisfy `a = q*b + r`. A nonzero floor remainder has the divisor's
sign. `CeilDiv(a, b)` is the mathematical ceiling for either divisor sign.
Alignment is ceiling division followed by multiplication by its positive alignment.
Floating division remains true division; the rounding attribute specifies integer operations.

The divisor must be nonzero. Signed minimum divided by -1 is outside the typed
domain (including remainder); statically known invalid inputs are located errors,
and the model checks dynamic inputs. Device execution requires valid inputs.
Operands must fit the result's integer domain without a lossy implicit conversion;
ambiguous mixed signed/unsigned operands require an explicit cast. The
compute/result dtype must match a typed operand: declaring a wider result alone
does not widen the operands before native arithmetic. Cast an operand first.
The final alignment result must also fit its declared type. Intermediate corrections must
not overflow: lowering uses quotient/remainder, never `a + b - 1`, negation of
signed minimum, or a floating approximation for i64/u64.

The `integer_division` Rewriter pass expands floor/ceiling into truncating native
quotient/remainder and sign/remainder corrections. Inserted operations retain source
provenance. Constant folders and both model modes implement the same modes before and
after expansion. A backend whose own integer `/` and `%` already round toward negative
infinity states so (`native_floor_divmod`) and keeps its floor division and remainder
unexpanded, because expanding them there prints the backend's own operators as the
truncating half of a correction it applies again — wrong for every negative dividend whose
remainder is not zero. Ceiling and alignment expand regardless, having no such operator.
A target's `//` spelling is a claim about that target and must be established for it, not
assumed from the surface: the qualified PyPTO device path rounds toward negative infinity
(upstream `5866c9b6f`, an ancestor of the supported minimum); CCE and PTO ISA truncate.
Every constant folder shares one evaluation
table for this domain; see [scalar simplification](0006-lowering-pipeline.md#integer-scalar-simplification).

With scalar simplification enabled, positive power-of-two floor remainders may
become equivalent low-bit masks. CCE/PTO keep other floor remainders compact
through the shared typed `FloorMod` helper, with the same domain and correction
rules above. The explicit expansion remains the diagnostic form and the lowering for
every backend that truncates. See [scalar simplification](0006-lowering-pipeline.md#integer-scalar-simplification).

### 6.11 Cross-core collective capacity and unaligned-store visibility

A5 public logical cross-core IDs are **0..10 inclusive** (11 IDs), and each
ID's counter has range **0..15**. The mode-4 AIC encoding adds 16 for AIV1,
mapping logical 0..10 to physical 16..26; this does not add public IDs.
These limits are separate from the eight intra-core `SetFlag/WaitFlag` IDs.
A collective publisher may be at most
15 generations ahead of any participant's consumption; completed generations
are reclaimed. Twenty sequentially consumed generations are legal. The model
tracks production and consumption independently for each member, flag and scope
(all cubes, all vectors, or vectors within one core). A wait releases when all
members have published its generation. This is separate from the eight IDs on
an intra-core pipe channel. The maintained A5 profile follows the user-selected
[CANN 9.0 CrossCoreWaitFlag contract](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0274.html).

A continuous unaligned register store commits data through the last complete
32-byte boundary. The trailing bytes remain in its store state until a contiguous
following store completes that block or `StoreUnAlignPost` flushes them. Each
state owns one cursor and pending suffix, and two states live at once are
independent: a second state storing elsewhere neither flushes the first nor
disturbs its bytes, and each Post writes only its own suffix (measured on A5).
Another cursor may not replace a state's pending cursor before Post. Reads before
Post observe only committed bytes. A Post writes its register's pending bytes
from the run's start to its own cursor position, which in a legal program is
exactly the pending suffix, because the cursor advanced with every store; a Post
on a state that has stored nothing therefore writes nothing. On a register an
earlier VF stranded it is not harmless: measured on A5, such a Post writes the
stranded bytes from that run's start lane up to its own cursor's lane, at its own
cursor's block, and drops the rest of the run. This follows the
[official continuous unaligned transfer description](https://asc.gitcode.com/guide/operator_practice/simd_operator_optimization/vector_compute/vf_optimization/continuous_unaligned_optimization.html).

The pending suffix is hardware state rather than program state: it stays in the
unaligned register, which outlives the state object, the VF call and the launch.
A VF that returns while one of its store states still holds bytes is therefore an
illegal program, not one that merely loses a tail. Measured on A5 (INT32, FP16
and UINT8): the suffix is never written at its own address; the next store that
reuses that register commits from the stranded run's start lane, so the stale
bytes land in memory before that store's own start and the new store's lanes
before that start are dropped; and this reaches across VF calls and launches.
The register picture — a start lane, an end lane and 32 bytes of data — is the
mechanism those measurements imply rather than a separately measured fact; it
reproduces every measured byte of the probes, and a rule anchored at the new
store's own lane does not. Which state reuses which register is a code-generation
decision, so the program has no defined reading; both model modes reject it where
the VF returns and name the store that stranded the bytes.

An unaligned store and its Post always post-update the cursor: A5 spells them
`vstus` and `vstas`, which advance by the stored count and by the Post's stride,
and it has no store form that leaves the cursor in place. `PostMode.NORMAL` stays
accepted on `reg_to_ub_unalign` and `reg_to_ub_unalign_post` through 0.1.x and
means `PostMode.UPDATE`; the frontend canonicalizes it, and IR that carries
`post_mode = normal` on either store op is rejected. Unaligned loads keep both
modes: a load without a stride does not advance its cursor.

### 6.12 Ordinary BF16 scalar conversions

The A5 CCE/PTO `bf16_scalar` pass materializes conversions at typed cell,
store and scalar-math boundaries. BF16 abs/sqrt widen to FP32, compute there,
then narrow to BF16 using round-to-nearest-even. Widening is exact, including
subnormals and signed zero. Infinities remain infinities; NaNs remain
NaNs, with scalar payload/sign unspecified. Widening can retain a
signaling NaN; it does not promise to quiet it. Narrowing and math results are
quiet. The target maps these explicit `scalar.cast`
operations to the SDK's public `AscendC::Cast` overloads, rather than a plain
C++ BF16 cast or a hidden codec. This ordinary scalar lowering does not qualify
BF16 SIMT math or remove PyPTO's separate ordinary scalar API gaps.

### 6.13 SIMT FP32 elementary functions

`simt.exp`, `exp2`, `log`, `log2`, `log1p`, `sin`, `cos`, `tanh` and `rsqrt`
take and return FP32. The model evaluates the function of the operand in
float64 and rounds once to FP32, nearest even; `rsqrt` is `1/sqrt(x)`. IEEE 754
special cases apply instead of host exceptions: overflow is +inf; `log` and
`log2` are -inf at ±0 and NaN below zero; `log1p` is -inf at -1 and NaN below
it; `sin` and `cos` are NaN at ±inf; `rsqrt` is ±inf at ±0, +0 at +inf and NaN
below zero. A NaN operand gives NaN without a sign or payload guarantee.

Measured on A5 with native Pro and imported CCE, `rsqrt` of 19 distinct
positive subnormal operands, from 2^-149 to the largest subnormal 0x007fffff, is
+inf, as if the operand were +0; FLT_MIN gives 2^63, and -2^-149 gives NaN, as
negative normal operands do. The model returns +inf for every positive subnormal
operand and NaN for every negative one (I020).

These operations are approximate across backends. Result bits and zero signs
are not part of the contract, tests state their tolerance, and RFC-0015 bounds
the A5 formulas. The model previously raised at these edges
(I019). Integral rounding keeps §6.3.

### 6.14 SIMT atomics

`simt.atomic { op }` is one indivisible read-modify-write of element `index` of
`dst`; `old` is the element's value immediately before it. `src` and `compare`
have the element dtype. Integer add and sub wrap modulo 2^width; f32 add and sub
round the exact result once to nearest even, with IEEE zero signs and overflow to
infinity. exch stores `src`; integer max, min, and, or and xor follow integer order
and bits; integer cas stores `src` when `old == compare`. f32 max stores `src`
when `src` is not NaN and `old` is NaN or less than `src`, with -0 less than +0;
min uses greater instead of less. f32 cas stores `src` when `old` has the bits of
`compare`, so +0 and -0 differ and equal NaN bits match. On u32, inc stores 0 when
`old >= src` and `old + 1` otherwise; dec stores `src` when `old == 0` or
`old > src` and `old - 1` otherwise. `old` is guaranteed for i32, u32 and f32 on
`gm` and `ub` and for i64/u64 on `gm`; other element types have no prior-value
guarantee. `simt.load`, `simt.store` and atomics copy f32 bits, including
signaling NaNs. Native A5 probes measured these rules (I023).
Atomics may overlap each other, while overlap with an ordinary load or store
needs ordering (§6.7). A result that depends on thread order is not defined by
the operation.

### 6.15 SIMT exact scalar math

`simt.mul_hi` operands and result share i32 or u32; the result is the high 32 bits
of the exact signed or unsigned 64-bit product. `simt.fma` rounds the exact f32
value `a*b + c` once to nearest even, with IEEE overflow and underflow. An exact
zero sum of nonzero terms is +0; a sum of zero terms is -0 only when both are -0.
Invalid operations and NaN operands give NaN without a payload or sign guarantee.
`simt.fmod` is the exact f32 remainder `a - trunc(a / b) * b`, which binary32
always represents, so it never rounds. A zero result keeps the sign of `a`; a
finite `a` with infinite `b` returns `a`; a NaN operand, infinite `a` or zero `b`
returns quiet NaN 0x7FC00000, as PyPTO Pro prints it. `simt.isnan`, `simt.isinf`
and `simt.isfinite` are i32 1 for a NaN, infinite or finite f32 operand, else 0.
The model had rounded FMA twice and rejected invalid fmod operands
(I021); the CCE fmod had rounded its quotient (I022).

### 6.16 FP32 scalar extrema

`scalar.max` and `scalar.min` on f32 are IEEE 754-2019 maximum and minimum in
either operand order: -0 orders below +0 and any NaN operand gives 0x7FFFFFFF.
A5 wrote those bits for quiet, signaling, negative, payload and paired NaNs from
PyPTO Pro `max((float)(a), (float)(b))` in vector sections, natively and through
CCE, and in cube sections. f32 scalar loads, cells and stores keep NaN bits, as
A5 echoed signaling NaNs. The model had followed operand order at equal values
and NaN and quieted loaded signaling NaNs (I032). C++ backends print Pro's
spelling. A5's compiler rejected it in a vector function ("max() in vector
function only supports integer types") before reaching its `min()`, and no other
spelling is measured there, so on A5 devices an f32 `scalar.max` or `scalar.min`
in a `vf` is invalid IR: the verifier reports each at its location before the
simulator runs or a backend prints. SIMT functions, with no measured spelling, report a gap.

## 7. Structured control flow and regions

Ops with regions own nested blocks; there is no `goto`, no unstructured jump.

```
%i = cf.for(%lo, %hi, %step) : i32 {          ; body may use %i; %lo/%hi/%step are i32 values
  cf.if(%c) {
    cf.break()
  } else {
    scalar.set(%acc, %t)
  }
}
```

Rules: `cf.break` / `cf.continue` appear only inside a `cf.for` (any nesting depth of `cf.if`);
`cf.for` bounds and step are integer scalar values/cells or integer literals; a literal zero
step is invalid. The verifier enforces this for directly constructed IR as well as frontend
output, so no backend receives a float comparison as an integer loop condition (M10-009).
`cf.return` appears only as the last op of a function; regions (`region.autosync`,
`region.side`) may nest inside control flow and vice versa; values defined inside a block are
not visible after it (a name bound in one `cf.if` branch and used after the `if` is a frontend
diagnostic, RFC-0002 §4.5). `cf.call @f(%args...) { cfg = {...} }` invokes a `vf` function;
`simt.launch @g(%args...) { threads = N }` launches a `simt` function.

The functional and pipe models execute SIMT threads cooperatively between block
barriers. Each thread retains its own scalar environment and structured program
counter. A barrier generation releases only when every launched thread reaches
the same barrier instruction. A thread exiting early, skipping a generation, or
waiting at another instruction while peers wait is a located divergence error.
Uniform repeated and loop barriers are supported. This establishes rendezvous
and visibility within a block; it does not impose a silicon warp scheduling order
or make a program with unsynchronized thread races well-defined.

There is no `cf.while` in v1: the DSL has no while loop.

## 8. Provenance

Every op carries:

| field | content |
|---|---|
| `#id` | a module-unique integer assigned by the frontend in source order. Passes keep ids of surviving ops and take fresh ids from `next_id`. Ids are never reused within a module. |
| `loc("file:line:col")` | the innermost DSL source position; inlined helper calls (RFC-0002 §4.3) push a call chain: `loc("a.py:12:4" <- "a.py:40:8")` |
| `origin([...])` | one entry per pass that inserted, rewrote or moved the op: `{pass, kind = inserted \| rewritten \| moved \| expanded, from = [#ids], note}` |

The module carries `source`, `source_sha256`, and `static = [...]` — one entry per
compile-time Python call the frontend evaluated (`{loc, expr, qualname, value_sha256}`), so a
kernel whose static parts changed can be told apart from one whose IR changed for another
reason.

These fields are what `ascriptor explain --op #9`, the interleaved dump
(`ascriptor dump-ir --interleave`), the annotated backend output (`// #9 dma.copy loc a.py:12`)
and the sim / board traces key on (D-015). Printers must print them; the verifier requires
`loc` on every op and `origin` on every op whose id is ≥ the frontend's final `next_id`.

## 9. Serialisation

Module metadata in Lowered IR may refer to values declared by its kernel-side
functions, such as the output parameters moved by `split_sides`. Text parsing
and JSON decoding resolve those references after reading the functions. Equal
name/type declarations duplicated on cube/vector sides denote the same metadata
value; missing or conflicting declarations are errors. This does not permit
forward references in operation operands or ordinary lexical attributes (M10-026).

### 9.1 Text form (`.ascrip`)

```
module      := 'module' '@' ident attrs? function+
function    := kind '@' ident '(' [param (',' param)*] ')' attrs? block
kind        := 'kernel' | 'vf' | 'simt' | 'func'
param       := value ':' type
block       := '{' op* '}'
op          := [results '='] opname '(' [operand (',' operand)*] ')' ((':' types) | attrs)* ['#' int] [loc] [block (ident block)*]
types       := type | '(' type (',' type)* ')'
results     := value (',' value)*
operand     := value | literal | '@' ident
attrs       := '{' [ident '=' attrval (',' ident '=' attrval)*] '}'
attrval     := literal | ident | value | '[' [attrval (',' attrval)*] ']' | attrs
loc         := 'loc' '(' string ('<-' string)* ')'
type        := ident ['<' typearg (',' typearg)* '>']
typearg     := type | dims | ident | int | value
dims        := '[' [dim (',' dim)*] ']'
dim         := int | ident | '?' | value | dim '*' dim
value       := '%' ident
comment     := ';' .* EOL
```

`origin` is printed as an attribute (`origin = [...]`). The result type and the attribute
block may be written in either order; the printer emits `: type` first. A second region is
introduced by its registry name (`} else {`). Opcodes always contain a dot, so a region body
(lines starting with `%` or an opcode) is never mistaken for an attribute block (`ident =`).
Whitespace and comments (`;`) are not significant; the printer emits one op per line, blocks
indented by two spaces, and the DSL source line above each op when `--interleave` is given.

Surface example — `tests/goldens/ir/matmul_float_mmad.ascrip`, hand-written in M1 and checked by
the round-trip tests (the frontend regenerates it in M2):

```
module @matmul_float_mmad { device = "950", ir = "surface/1", mode = "mix", source = "kernels/a5/matmul/matmul_float_mmad.py", next_id = 10 }

kernel @matmul_float_mmad_kernel(%x: gm<f32, [%M, %K]>, %y: gm<f32, [%N, %K]>, %z: gm<f32, [%M, %N]>, %M: i32, %N: i32, %K: i32) { outputs = [%z] } {
  %l1x = mem.alloc() : l1<f32, [%M, %K], nz> { name = "l1x" } #1 loc("kernels/a5/matmul/matmul_float_mmad.py:6:4")
  %l1y = mem.alloc() : l1<f32, [%N, %K], nz> { name = "l1y" } #2 loc("kernels/a5/matmul/matmul_float_mmad.py:7:4")
  %l0c = mem.alloc() : l0c<f32, [%M, %N]> { name = "l0c" } #3 loc("kernels/a5/matmul/matmul_float_mmad.py:8:4")
  region.autosync() #4 loc("kernels/a5/matmul/matmul_float_mmad.py:9:4") {
    dma.copy(%l1x, %x) #5 loc("kernels/a5/matmul/matmul_float_mmad.py:10:8")
    dma.copy(%l1y, %y) #6 loc("kernels/a5/matmul/matmul_float_mmad.py:11:8")
    cube.matmul(%l0c, %l1x, %l1y) { m = %M, n = %N, k = %K, init = true } #7 loc("kernels/a5/matmul/matmul_float_mmad.py:12:8")
    dma.copy(%z, %l0c) #8 loc("kernels/a5/matmul/matmul_float_mmad.py:13:8")
  }
  cf.return(%z) #9 loc("kernels/a5/matmul/matmul_float_mmad.py:14:4")
}
```

Shape symbols in signatures are the scalar parameters themselves (`%M`), so a GM type and the
scalar that sizes it are one value; `cube.matmul` is the Surface shortcut that `desugar`
expands into `dma.l1_to_l0` + `cube.mmad` loops (§12).

Lowered fragment of the same kernel (cube side):

```
func @matmul_float_mmad_kernel.cube(%x: gm<f32, [M, K]>, %y: gm<f32, [K, N]>, %z: gm<f32, [M, N]>,
                                    %M: i32, %N: i32, %K: i32) { side = cube } {
  %a_l1 = mem.alloc() : l1<f32, [32, 16], nz> { addr = 0 } #1 loc(...)
  %a_l0 = mem.alloc() : l0a<f32, [32, 16]> { addr = 0 } #3 loc(...)
  %e0 = sync.event() : event<1, MTE2, MTE1, 0> #14 loc(...) { origin = [{pass = "autosync", kind = inserted, from = [7, 9], note = "RAW %a_l1"}] }
  dma.gm_to_l1.nd2nz(%a_l1, %x) { pipe = MTE2, rows = 32, cols = 16, src_stride = %K } #7 loc(...) { origin = [{pass = "device_lower", kind = rewritten, from = [7]}] }
  sync.set(%e0) { pipe = MTE2 } #15 ...
  sync.wait(%e0) { pipe = MTE1 } #16 ...

}
```

### 9.2 JSON form

The same structure as the text form, one object per op:

```json
{"ir": "surface/1", "name": "matmul_float_mmad", "attrs": {"device": "950", "mode": "mix", "next_id": 12},
 "functions": [{"kind": "kernel", "name": "matmul_float_mmad_kernel",
   "params": [{"name": "x", "type": "gm<f32, [M, K]>"}, ...],
   "attrs": {"outputs": ["%z"], "block_dim": "1"},
   "body": [{"id": 1, "op": "mem.alloc", "results": ["%a_l1"], "type": "l1<f32, [32, 16], nz>",
             "operands": [], "attrs": {}, "loc": ["matmul_float_mmad.py:14:4"], "origin": []},
            {"id": 6, "op": "region.autosync", "results": [], "operands": [], "attrs": {},
             "loc": [...], "regions": [[...]]}]}]}
```

Types and dims are stored as their text spelling; there is one type grammar. Text and JSON
are equivalent; `to_json(parse(text)) == to_json(from_json(json))`.

### 9.3 Python API

`Module`, `Function`, `Block`, `Op`, `Value`, `Type` are frozen dataclasses (`ir/core.py`,
`ir/types.py`). `print_module(m, source=...)`, `parse_module(text)`, `to_json(m)`, `from_json(obj)`,
`verify(m)` / `check(m)`. Construction goes through `Builder` (`function`, `op`, `region`, `loop`,
`if_`, `cell`, `ret`; ids assigned in pre-order, names made unique) and passes through `Rewriter`
(`make` for new ops with fresh ids and an `origin` entry, `rewritten` for changed ops, `rewrite(fn)`
to map over every op, regions included).

### 9.4 Versioning

`ir` is `<level>/<major>`. A reader accepts a document whose major it knows. Additive changes
(new attribute, new opcode, new dtype) do not bump the major; unknown **attributes** are
preserved verbatim by parser and printer so an older reader round-trips a newer document;
unknown **opcodes** are errors (the registry is the truth). Semantic changes to an existing
op (operand order, meaning of an attribute) bump the major and the opcode must be renamed or
the old spelling retired in the same change. The registry export `ops.json` carries the same
major.

## 10. Lowered IR invariants

In addition to Surface invariants:

1. The kernel is replaced by `func @k.cube` and `func @k.vec`, each with `side`; for
   `mode = vec` only the vec side exists, for `mode = cube` only the cube side.
2. Every op has an effective pipe from its registry entry or, for an opcode
   whose schema defines it, an explicit `pipe` attribute. Fixed-pipe opcodes
   do not carry an extra attribute; the registry remains authoritative.
3. No `region.*` remains; every sync is explicit (`sync.set` / `sync.wait` with pipes and an
   event id; cross-core ops with flag ids; `sync.barrier` where the DSL wrote one).
4. Every `mem.alloc` has `addr` and its extent lies inside the device capacity of its position,
   per `addr_alloc`; slots of a `buf` are laid out contiguously.
5. Every `dma.*` and `cube.*` op is a device-specific opcode (`level = lowered`).
6. `list.*` reads are `list.load_ptr` / `list.load_dim` with literal descriptor offsets (§13).
7. Every scalar value is `i32`, `i64`, `f32`, `b1` or a cell thereof; narrower scalars were
   widened by `desugar` and the original dtype kept as a `cast` attribute where a backend needs it.
8. `outputs`, `block_dim`, `workspace` and `crosscore` are on the module `meta` attribute so the
   launcher reads them without walking functions.

A module violating any of these is rejected by every backend's `compile` before it looks at
a single op; the message names the invariant.

## 11. Verifier

Implemented in M1 (`ir/verify.py`): unknown opcodes; level and function-kind admissibility;
device availability; operand count and pattern unification (variables shared across operands,
value-attributes and results); result count and patterns; unknown, missing-required and
mistyped attributes; region counts; `cf.break` / `cf.continue` inside a loop; terminators
last; `cf.return` at top level; region scoping of values; duplicate op ids; duplicate
definitions; dimension values in scope and integer-typed; register types only in `vf`, events
and flags only in kernels, `gmlist` only as parameters, no `?` on chip; cells read before any
`scalar.set` without `init`; `cf.call` / `simt.launch` targets of the right kind; outputs are
parameters; exactly one kernel per surface module. Deferred to the passes that establish them
(M4): capacity and overlap, event pairing, the autosync-region rule, pipe presence on lowered ops.

The full rule set:

Structural: unique op ids; SSA definitions dominate uses; blocks well-nested; `cf.break` /
`cf.continue` inside a loop; `cf.return` last; exactly one `kernel` (Surface) or one `func`
per side (Lowered); `vf` functions contain only allowed namespaces; `simt` likewise.

Typing: every operand matches the registry pattern with unified type variables; results have
the declared types; dtype allowed on the module's device (on A5, no f32 `scalar.min` /
`scalar.max` in a `vf`, §6.16); dims of local allocations literal;
`?` only in `gmlist` member types; product dims contain only symbols and literals; view
extents inside the base (when static).

Semantics: cells are set before read on every path; events are set and waited on the same
side with matching depth; every `region.autosync` contains no explicit `sync.set` / `wait` on
buffers it manages (the old rule); `outputs` are parameters; a written GM parameter that is
not an output and not a workspace is a warning; `block_dim` references only signature
symbols.

Capacity (Lowered): per position, allocations do not overlap and fit the profile; per side,
only that side's ops. Every backend runs the verifier on entry.

An allocation's extent is what the hardware **writes** into it, not what its dims say. An L1 tile
is the case in hand: both on-chip layouts pad, and differ only in the column granule, so
`addr_alloc` reserves

    align16(rows) * align_up(cols, G) * width        G = 16 for ZZ, else C0 = 32 / width

NZ keeps `ceil(cols / C0)` fractal columns of `dstNzC0Stride = align16(rows)` rows each; ZZ — the
c220 cube's layout for **fp32 and nothing else** — keeps `rows / 16` bands of `align16(cols) * 16`
elements. Reserving the logical size instead let two adjacent tiles satisfy this invariant and
still overlap on the card, the one loaded first losing its upper half.

Two things that cost a day there. **The layout is chosen by the dtype, not by its width**: the
backend selected ZZ with `sizeof(T) == 4`, so i32 tiles were written and read as ZZ while the
allocator and the model had them as NZ — a self-consistent backend disagreeing with everything
above it. And **nothing below a card can object**: D-022 makes every on-chip tensor logical
row-major and every DMA a window copy, so `sim` and `pipesim` model no physical layout and an
overlapping write is invisible to them by construction. A transfer whose physical footprint
exceeds its logical one belongs here, in the reservation — nothing downstream will notice.

## 12. The pass pipeline

`verify → desugar → device_lower → gmbuff → crosssync → autosync → events → addr_alloc →
split_sides → events_restamp → dce → local_mutex → mutex_coalesce → scalar_simplify →
liveness → verify` (amended by RFC-0006 §3 / D-029: `autosync`, `events` and `addr_alloc` run
before the split so that cross-side hazards are seen in one graph and both sides share every
address; and by RFC-0005 §3.1: `crosssync` carries the cross-side checking that used to sit
inside `autosync`, so that it reaches a kernel with no `region.autosync` in it). Each pass is a function `Module -> Module`, registered with a name, the levels it
accepts and produces, and the invariants it establishes; the pass manager verifies between
passes and records `origin` through the `Rewriter`. `ascriptor dump-ir --after <pass>` prints the
module after any pass; `--explain` prints the decisions of every pass run (autosync: hazard
edges and events; addr_alloc: the layout; events: channel assignment); `ascriptor explain --op N`
follows one op through them. RFC-0006 specifies the passes and the pipe-level simulator.

## 13. ListDescriptor v1 (launcher ↔ kernel ABI for `gmlist`)

A `gmlist` parameter reaches the kernel as one GM pointer to a descriptor. The descriptor is
written by the launcher and read by the kernel with plain scalar loads:

| field | type | meaning |
|---|---|---|
| `count` | `u32` | number of members |
| `max_rank` | `u32` | number of dims stored per member (the rank of the member type) |
| `members[i].ptr` | `u64` | GM address of member `i` |
| `members[i].dims[0..max_rank)` | `i64` | member dims; shared (symbol) dims are repeated for checking |

The byte layout is AscendC's `ListTensorDesc` in its DYNAMIC form, transcribed 2026-08-28 from
CANN 9.0.0's `dav_c310/kernel_operator_list_tensor_impl.h` (`ListTensorDecode`, D-048): a
sequence of `u64` words — word 0 is the byte offset of the pointer array; from word 1 every
member has a header `(index << 32) | rank` followed by `rank` dims (`u64`); the pointer array
holds one GM address per member, so the descriptor is `8 + count * (1 + rank) * 8 + count * 8`
bytes. The count is the pointer-array offset divided by the per-member size — CANN's own
consistency rule; the header's high half is a framework word (1 for every member on the board
and under cannsim, probed 2026-08-28), so a reader must not take it for the index or the count.
The aclnn launcher passes CANN's own descriptor
untouched (the op declares the parameter `ParamType(DYNAMIC)` — as an input or, for a list the
kernel returns, as an output — and the host hands over an `aclTensorList` either way, RFC-0007
§7; an output list's descriptor carries the shapes of the caller's member tensors, D-060); the
sim launcher binds the members directly (a Python list of tensors) and never builds the bytes.
The wrapper `GMList<T>` of `tensorutils_cce.h` reads the descriptor with plain scalar loads
(`count()`, `ptr(i)`, `dim(i, d)`), the same for an input and an output list.

Surface ops: `%n = list.count(%xs) : i32`, `%d = list.item_dim(%xs, %i) { dim = 0 } : i32`,
`%t = list.item(%xs, %i) : gm<T, [%d, D]>` — the frontend reads every `?` dim with
`list.item_dim` first and types the member with those scalars, so no `?` survives past the
parameter type. The three ops stay through lowering and the backend prints the descriptor
reads itself; `list.load_ptr(%xs, %i)` / `list.load_dim(%xs, %i) { dim = 0 }` (with the
descriptor offsets as attributes) remain the reserved explicit forms for a pass that wants the
layout in the IR — no pass produces them yet. A loop over a list is `cf.for(0, %n, 1)` with
`list.item` inside; indexing with a literal works the same; `GMList[..., count=n]` pins the
count and unrolls.

## 14. Device profile

`ascriptor/devices/profiles/<device_type>.json` is the only place silicon facts live: arch,
core counts, per-position capacities, toolchain identifiers. The IR names the device type;
passes and backends read the profile. No layer hard-codes a capacity.

## 17. Open questions (resolve by appending to `docs/decisions.md`)

1. Whether `scalar` widening (§10.7) should keep `i16` / `u8` scalar cells for `vf` functions
   where the hardware has narrow scalar registers, or widen uniformly. Default: widen; revisit
   when the first kernel needs it.
2. Whether `region.autosync` should be the default for a kernel body (as some old kernels
   assume) or always explicit. Default: explicit `with autosync():` in the DSL, region in the IR.
3. Complex dtypes (`c32`, `c64`) remain in the dtype table with per-operation/device
   availability. A5 register examples qualify their explicitly tested complex operations;
   the A2-only premise does not describe this source release.


### FP32-to-FP8 NaN fields

For the qualified A5 nearest-even FP32-to-E4M3/E5M2 vector cast, converted NaNs
use the canonical byte0x7f. This includes either sign and tested quiet/signaling
FP32 NaN payloads. E4M3 finite overflow and either infinity also produce0x7f;
E5M2 infinities retain their signed infinity encodings. Signed zero remains
signed. The source-width/rounding scope is explicit; this observation does not
qualify other cast forms or saturation settings (M10-046).

The separately qualified A5 scalar FIXPIPE E4M3 path encodes finite scaled
overflow as canonical NaN byte `0x7f`, including negative overflow. The
nearest-even endpoints at `+/-464` remain signed finite `+/-448`; finite
underflow preserves its zero sign. M10-050 records the direct-GM scale-0.5
hardware case and generated regressions. It does not qualify FIX input
NaNs/infinities, E5M2, or an unmeasured destination/rounding path.


### Bias-table conversion and VF floating rounding

On A5, `dma.l1_to_bt` accepts same-dtype transfers and f16/bf16 L1 sources
widened to an f32 bias table. Other cross-dtype pairs are rejected with the
operation's source location; an existing CCE widening instruction must not be
rejected by an accidental shared type variable in the IR schema (M10-048).

A VF floating cast applies its declared rounding mode. Nearest-away selects
the endpoint farther from zero at an exact tie. FP16 round-to-odd truncates
and sets the low significand bit for inexact finite values, preserving exact
values and both zero signs. BF16 round-to-odd has no qualified CCE form and
remains a located gap. Supported ROUND/ODD must not silently use nearest-even
in the simulator (M10-049).
